# PiGroups Pi 适配器 概念稿

> 版本：v1.0
> 平台侧的权威文档在 `../PiGroups/docs/`。本文只讲**适配器**。

---

## 1. 它是什么

一个 Pi 扩展。把它装进一个 pi session，那个 session 就成为一个 PiGroups 成员：它有身份、在群里说话、能拉起下级、能被上级打断。

平台那一侧刻意什么都不懂——不懂 agent 是什么、由谁拉起、如何唤醒、死没死。**所有这些都落在这里。**

---

## 2. 为什么需要它

假设没有适配器，只有平台：一个 agent 收到任务，干完，**不说话**。平台不会催——它不解释内容，也不判断谁该说话。于是发起方永远等，两边都停在 idle。

这不是 bug，是平台的设计：它只保证送达，不保证任何人开口。**"会开口"是适配器的责任。**

适配器要兜住三类事：

| 现象 | 本质 |
|---|---|
| `find ~/` 卡死四十分钟 | 工具无界，进程活着但不动 |
| 429 重试用尽，那一轮带着错误结束 | 错误被当成了完成 |
| 干完活没回复，两边都 idle | "完成"没有定义 |

三者的共同点：**都已经超出"提示词能保证"的范围**。所以规矩写在代码里，提示词只负责减少触发。

---

## 3. 核心图景

适配器全部跑在那**一个** pi 进程里。没有守护进程、没有旁路服务。

```
┌─ pi session ────────────────────────────────────┐
│  extension   注册 pg_* 工具、挂 pi 的事件、暴露     │
│  PiSurface   deliver / abort / onSettled / 忙不忙  │
│                                                  │
│  loop        拉取 → 分类 → 注入 → 义务 → 遥测      │
│              （与 pi 无关，只依赖 PiSurface）       │
│                                                  │
│  Herdr       拉起下级、读 pane、发按键、关 pane     │
└──────────────────────────────────────────────────┘
        │ HTTP /v1                        │ herdr CLI
        ▼                                 ▼
   PiGroups 平台                    子成员的 pane
```

`PiSurface` 和 `Herdr` 都是接口，在测试里可以被假实现替掉——这是这个仓库能被测的唯一原因。

## 4. 职责边界

| | 平台 | 适配器 | 成员的提示词 | skill |
|---|---|---|---|---|
| 结构、消息、指令路由 | ✓ | | | |
| 持续拉取、**不依赖空闲** | | ✓ | | |
| 拉起下级、读 pane、打断 | | ✓ | | |
| **"有没有该回没回"** | | ✓ | | |
| 该不该回这条消息 | | | ✓ | |
| 怎么回、被卡住怎么办 | | | | ✓ |

一条贯穿的规矩：**机械保证放适配器，减少触发放提示词。** 只有适配器会变成"处处打断、什么都不信"；只有提示词就会"模型忘了就完蛋"。

## 5. 三个失败模式怎么解

### 5.1 挂住

- **拉取不挂在"空闲"上**：只要进程活着就持续拉。否则一个卡死的成员永远收不到"打断"这条指令，连人都没法通过平台叫停它。
- 打断 = `PiSurface.abort()`，它切断正在跑的那一轮（思考、输出、工具调用）。**不是暂停，是切断。**
  - **实机测出来的边界**（2026-11-01，`probe/logs/run-20261101T1920-ignore-signal/`）：一个**不响应 abort signal 的工具不会被切断**——它跑满自己的 60 秒才返回，那一轮在那之后才结束（abort 后 3009 ms 放弃等待，settle 晚到 58 296 ms）。所以"切断"成立的范围是 pi 自己控制的部分：模型输出、等待、以及会响应 signal 的工具。对一个卡在不响应 signal 的工具里的成员，`pg.abort` 只是一次请求；**真能停住它的是关掉它的 pane**（删成员走的就是这条路，不是发 abort）。这不是缺陷，是接口边界——但它必须写在这里，否则"发个 abort 就停了"是个会骗人的承诺。
- 打断之后不注入"你在哪被打断"之类的提示。被中断的 tool result 就在 transcript 里，模型自己看得见。

### 5.2 错误被当成完成

Pi 自己会重试，重试用尽后那一轮带着错误结束。适配器**不做退避**——那会和 Pi 的内建重试打架。

它只做一件事：**把"这一轮结束了"和"任务完成了"分开**。结束不产生任何结论。

### 5.3 沉默的 idle

核心约定：

> **任务由消息开具，也由消息关闭。不说话不算完成。**

- 适配器维护"欠回复"：某个会话里，最后一条消息是别人发给我的（点名我、或来自我的父），而我没有再说过话。
- 这个状态**从平台的历史里算出来**，不存本地——重启后天然恢复。
- **对端已经不在的会话不算欠**。一对一里对方被删了，这条债永远还不上（发过去只会得到"成员已不存在"），留着它只会让活着的那个被反复催一件做不到的事。所以"谁还活着"是义务谓词的一部分，不是优化。
- 到 idle 还欠着，就催一次：回复，或说明为什么不需要回。
- 催的次数用尽仍无产出，适配器**自己**上报 `blocked`。

一条界线：

> **适配器可以替成员报告"卡住了"，但永远不能替它报告"做完了"。**

前者是操作事实（进程没产出），适配器有权威；后者是任务结论，只有 agent 有权威。

## 6. 遥测：让上级看得见，但不淹没它

下级出事，上级不该靠"猜它为什么没声音"。

- **只向上一级报**。控制通道本来就只能同群可达，所以一个管理者只看得到直接下级。再深的事由中间那层汇报——人被排除在外，它能看全树的全部遥测。
- **边沿触发**：状态变化时报一次（卡住、出错、恢复），不是周期上报。429 会被 Pi 重试很多次，每次上报都提醒等于把同一个问题提醒七遍。
- **上级侧合并**：第一个未处理事件开一个窗口，窗口内的所有事件折成一条提醒。窗口到期时如果一切都恢复了，**静默取消**——不发"一切正常"。
- 提醒**不打断正在干活的上级**，挂到下一次空闲。

---

## 7. 它不做什么

| 不做 | 原因 |
|---|---|
| 命令白名单 / 拦截 `find` | 不属于这个插件；执行环境该管的事 |
| 429 自己的退避重试 | Pi 已经重试了 |
| 相关性分类器（yes/no 门控） | 平台的廉价信号已经够用；门控在小队里是净亏 |
| 跨层遥测汇聚 | 一级够用，人是兜底 |
| 界面 | 界面是平台上另一个消费者 |
| 改平台 | 平台只按 token 和 HTTP 交互，适配器不该要求它多懂一点 |

## 8. 三个不显然但必须成立的判断

**① 拉到的消息要先落盘再注入。**
平台的投递是"取走即消费"。适配器如果在取走之后、注入之前崩掉，那条消息就永远消失了，而且没人会发现。所以注入前必须写一份日志，重启后重放。

**② 注入文本要带消息号。**
重放可能造成重复注入。把编号写进文本（`[g:m_abc#89]`），模型能自己认出"这条我处理过"。

**③ 一个成员一个进程。**
平台对同一成员的并发 `poll` 会拒绝（409）。这不是限制，是提醒：同一个身份被两个进程驱动，两条投递流会互相偷消息。
