# PiGroups Pi 适配器 概念稿

> 版本：v3.0（待审）
> v3 的依据是 2026-11-01 的真机实验（`probe/logs/steer-20261101T170244Z/`），它推翻了 v2.x 里
> 关于"steer 送到就算看到"的假设：**一个正在跑长工具的成员，steer 要等工具返回才看得到；
> 而 steer 之后紧接着 abort，那条消息会彻底丢失**。§8 按测量结果重写。
> 平台侧的权威文档在 `../PiGroups/docs/`。本文只讲**适配器**。
>
> v1 只讲"为什么要它"。v2 补了工作流、能力、工具面、事实归属。
> **v2.1 修掉 v2 的一个结构性错误**：v2 把平台的三件事（可达性、会话、指挥权）揉成了
> "层级"一件事，于是漏掉了平台真实存在的能力——**任意两个成员可以私聊**——以及承载它的
> 工具（名册）。同时补上**名词定义表**：同一个词在平台、pi、herdr 三层里含义不同，
> 这已经是本仓库几次事故的共同原因。

---

## 1. 它是什么

一个装在 pi 里的扩展。装进去之后，那个 pi session 就**成为一个组织的成员**：有身份、在群里说话、
能拉起下级、能被上级叫停、能被人看见。

一句话的定位：

> **它把"一群 pi 会话"变成"一个有层级的团队"。**

平台那一侧刻意什么都不懂——不懂 agent 是什么、由谁拉起、如何唤醒、死没死。平台负责自身服务的端口绑定、平台身份识别与当前 endpoint 持久化；**agent 的创建、存活、唤醒与修复仍由适配器负责。**

## 2. 名词定义表

**这一节存在的理由**：同一个词在三层里含义不同，而误用它们已经出过两次事故
（把 herdr 的"忙不忙"当成员就绪；把 pi 的 `isError` 当工具成功）。
**每个词都标明属于哪一层。没有标注层次的词，不许出现在代码和文档里。**

### 2.1 平台层（PiGroups）

| 名词 | 定义 | 容易混淆的 |
|---|---|---|
| **成员** | 持有 token 的实体，有父、有名字、状态是 alive 或 gone | **不是** pi 的 session。一个 pi 进程带上 token 才成为成员 |
| **根** | 没有父的成员；不能被删除 | — |
| **父 / 子 / 兄弟** | 树上的结构关系；兄弟 = 同一个父的两个子 | 兄弟**不是**"平级同事"的意思，它们天然在同一个群里 |
| **名册** | `GET /v1/tree` 返回的全部 alive 成员（id、名字、父、子数、最后活跃） | **不是**"我的下级"。我的下级只是名册的一部分 |
| **群** | `{owner} ∪ owner 的 alive 子成员`。**结构性的**：不能加入、不能退出、不能邀请；owner 没有 alive 子成员时这个群不存在 | 不是频道，不是可以拉人的聊天室 |
| **一对一 / DM** | 两个成员之间的会话，id 是 `dm:较小id_较大id`。**任何两个 alive 成员之间都可以有**，不受树约束 | 不能 @ 人；群里的第三方看不到 |
| **会话（conversation）** | 群或一对一的统称，是消息的容器，有自己的序号 | **不是** pi 的 session（见 2.2） |
| **消息** | 会话里的一条，有 `seq`、发送者、正文、`mentions` | — |
| **指令（control）** | `cmd` + `payload`，平台**不解释**；有投递回执 | 不是消息。消息给人看，指令给适配器看 |
| **投递 / 回执** | 平台认为已送达 | **不是"已读"**。平台没有读状态 |
| **取走即消费** | `poll` 把消息交给成员并从队列删除 | 所以"取走"之后崩掉就是永久丢失——这是适配器要 journal 的原因 |
| **gap** | "有若干条旧消息已被折叠，没有逐条给你"的信号 | 它不是一条消息，不能当消息注入 |
| **`last_seen_at`** | 鉴权时刷新的时间戳：**证明这个 token 最近被用过** | **不是心跳**（心跳是另一个专用时间戳，平台 §9.1），也**不是"活着"** |
| **alive / gone** | 成员状态。gone 之后：不能再收发、`poll` 回答 410、名字可被复用？——不可复用，名字是唯一索引的一部分 | — |

### 2.2 pi 层

| 名词 | 定义 | 容易混淆的 |
|---|---|---|
| **session** | 一个 pi 进程的上下文与历史文件 | **不是**平台的"会话" |
| **回合（turn）** | 从 `agent_start` 到 `agent_before_settle`（或 abort 后的 `agent_settled(aborted:true)`） | **"回合结束"不等于"任务完成"** |
| **settle** | 一轮结束后 pi 通知"我空闲了"的回调 | **它不再是投递的触发器**（v3 起由时间窗触发）；它现在只用来评估义务与遥测 |
| **工具调用** | 模型发起的一次工具执行，有 `tool_execution_start` / `end` | `isError:false` **不代表成功**——被切断的工具也是 false |
| **接受消息** | `sendMessage` 返回。**只表示 pi 收下了** | **不保证起了一轮**。这是已知缺口（§10 D2） |

### 2.3 herdr 层

| 名词 | 定义 | 容易混淆的 |
|---|---|---|
| **pane** | 一个终端面板；里面跑着一个进程 | — |
| **`agent_status`** | herdr **为自己界面推断的**状态：`idle / working / blocked / done / unknown` | **不是**协议，不是"成员就绪"。`done` 只是它 UI 上的说法 |
| **"agent 不在 pane 里了"** | herdr 停止追踪那个 pane 的 agent | 是**观察**，不是"pi 退出了"这个事实 |

### 2.4 适配器层（本文定义的）

| 名词 | 定义 |
|---|---|
| **循环（loop）** | 拉取 → 分类 → 注入 → 义务 → 遥测。与 pi 无关，只依赖 `PiSurface` |
| **注入（inject）** | 把一条消息变成一次 `deliver`，让模型看得见 |
| **journal** | 注入**之前**落盘的那份批次；投递成功后才提交。重启时重放 |
| **水位（watermark）** | 每个成员、每个会话"已经注入到第几条"。**按成员分**，因为父子共用一个目录 |
| **欠回复 flag** | 三类消息置起它：一对一里每一条、点到我的名、来自我的父（群的 `@all` 也只置一条）。**由回复或 `pg_ack` 清掉**。一个会话一个 flag，覆盖它之前的全部消息 |
| **确认（ack）** | `pg_ack` 清掉一个会话的欠回复 flag，**不发任何消息**。与回复在账本上等价，区别只在于没有消息 |
| **催办（nudge）** | 到空闲还欠着时，投一次"你有账没结" |
| **提醒（reminder）** | 下级出事后，给上级的一条合并消息 |
| **`blocked`（适配器上报）** | 催了几次仍无产出 → 适配器**替成员**报告"卡住了" | **和 herdr 的 `blocked` 无关**，也和"任务失败"无关 |
| **数据目录（adapter dir）** | 一台机器上本插件唯一的落盘根：`~/.pi/pigroups`（自定义 profile 时在 `<PI_CODING_AGENT_DIR>/pigroups`）。journal、水位、账本、`orgs/` 与复活用的两份记录都在里面（设计说明 §12.1） | 跟着 Pi 自己的惯例，**不在 HOME 下另开一个 `.xxx` 目录**；换 profile 就换目录 |
| **复活（respawn）** | 进程没了、成员还在（重启/崩溃/关 tab）→ 用记录里的 `sessionFile` 与 `token` 把 session 重新打开并恢复平台绑定，**成员 id 不变** | 被删的成员（`gone`）身份不可复原，那不是复活；`intent:terminated` 的永不自动拉起 |
| **就绪（ready）** | 适配器派生的事实，见 §9 D1 |
| **关系（relation）** | 名册里每个人与我的结构关系：`self / parent / child / sibling / peer` | **关系 ≠ 权限**。只有 `child` 能被 `pg_abort`；`sibling`/`peer` 能说话但不能指挥（§9 D6） |
| **预约（schedule）** | 成员让适配器在未来某一刻把自己唤醒一次 | 不是周期任务，平台也没有延迟投递；只在进程内有效 |
| **开组织（org start）** | 一个还没有身份的会话自己找到平台代码、必要时把平台拉起来、`POST /v1/bootstrap` 拿到根身份，然后才成为成员 | **不是"注册成员"**：它只能创建根；成员仍然只能被别人创建。也不是"加入别人的组织"——那还是环境变量 |

## 3. 三层的职责，以及适配器站在哪

这套系统里有三个别人写的组件，和一个我们写的。**分清谁拥有哪个事实，是这个仓库最重要的一条纪律。**

| | 拥有什么 | 不拥有什么 |
|---|---|---|
| **PiGroups 平台** | 组织：成员树、名字、token、alive/gone、**名册**；会话与消息（每会话序号、取走即消费、gap）；不透明指令；投递回执；`last_seen_at`；**谁可以给谁发消息（人人可达）、谁可以与谁交换指令（必须同群）**；自身 listener 的端口绑定、平台身份与当前 endpoint | 回合、工具、agent 进程/pane、模型、成员是否活着、重启/respawn、相关性、紧急程度。**它不知道 agent 是什么** |
| **pi** | 会话：一轮回合的开始与结束、消息是否被接受、工具是否在执行、`isError`、session 文件 | 这条消息对 PiGroups 意味着什么 |
| **herdr** | 终端与进程：pane/tab、某个 pane 里跑着什么、按键回显、滚动缓冲；**以及它为自己界面推断的 `agent_status`** | 那个 pi 是不是一个成员、它有没有连上平台、它准备好没有 |
| **适配器** | 三者之间的**全部跨层语义**：成员就绪、已投递、回合结束、被切断、可达而不该发、欠回复、卡住；**指令能不能作用到这个成员**；journal、水位、义务、遥测、pane 映射、催办策略 | 组织本身（平台的）、回合内容（pi 的）、进程（herdr 的） |

由此得出贯穿全文的一条规则：

> **每个事实只能从它的拥有者那里取。适配器可以"派生"事实，但派生必须写明推导方式，并且知道它不等于原事实。**

特别注意中间那一行：**平台拥有"这两个人能不能交换指令"（同群即可），但"这条指令能不能作用到这个成员"是适配器的规矩**——`sharesGroup` 对父子**双向为真**，是适配器用"只认上级"把它收窄成单向的。这类"平台允许、适配器限制"的地方必须写出来，否则下一个人会以为平台在管。

## 4. 它服务什么工作流

适配器不是"帮我跑一个子任务"的工具。**一次性子任务用 subagent 更便宜**——那是同一个进程里的
派生，没有身份、没有组织、任务结束就消失。

适配器服务的是**需要组织的事情**。

### 4.1 派活—汇报（最基本的一条）

```
人 ──任务──▶ 根成员 ──pg_spawn + 简报──▶ 子成员 A / B / C
                    ◀──pg_say（结论）──────┘
                    ──汇总──▶ 人
```

**任务由消息开具，由消息或一次确认关闭。** 上级不靠"进程还活着"判断进度，靠下级开口。

### 4.2 持续值班（长期团队）

同一个组织长期存在，接一批又一批任务。成员保留自己的 session，**上下文是连续的**：
上一个任务的结论、踩过的坑，下一个任务还能用。这是 subagent 做不到的。

### 4.3 卡住处理

某个成员卡在工具里、某个回合带着错误结束、某个成员半天不说话。
上级看到遥测、必要时 `pg_inspect` 问一句、看它最后一轮在干什么 → 判断 →
`pg_say`（改方向）或 `pg_abort`（切断）或 `pg_terminate`（换人）。

### 4.4 升级

下级需要拍板，但决定超出它的范围：`pg_say` 给上级，等回复。**等待本身不消耗回合**——
它只是欠一条回复，而欠回复由适配器盯着。

### 4.5 组织变更

活多了一个人干不完 → `pg_spawn`；某个分支没有存在的必要 → `pg_terminate`（级联删子树）。
组织是**活的**，不是启动时定死的。

### 4.6 平级协作（v2 漏掉的一整类）

**两个不同群里的成员直接私聊**，不经过任何上级。

```
A1 ──dm──▶ B2        两个不同父的两个子，平台允许，不需要谁批准
```

这是平台明确的能力（平台概念稿 §5.2：「任何成员都可以给另一个成员发一对一消息，不受树约束」），
用途很实在：A 的子成员发现 B 那边的接口变了，直接问 B 的子成员，**不必先报告两个上级再逐层转达**。

**前提是知道对方的 id**——所以 §6 的 F0 发现不是可选项。

### 4.7 发现（先找人，再说话）

拿到名册 → 按名字认出要找的人 → 一对一联系。没有这一步，成员只能回复"已经跟它说过话的人"。

### 4.8 重启之后（把组织接回来）

机器重启、进程崩了、tab 被关了——平台里的成员**还在**（它只是一行数据），死的是跑它的进程。这时整棵树
是"形在神亡"：名册、会话、消息全都在，但没有人回话。

恢复它需要两样平台不知道的东西：**每个成员的 session 文件**（谁能重开它）和**它的 token**（重开之后
怎么认回自己）。这两样只有适配器知道，所以复活是适配器的事，不是平台的事。

平台先恢复到同一 `platform_id` 的正常服务，适配器跟随平台持久化 endpoint 的实际地址。
启动期身份/版本可用不等于成员接口已就绪；health 超时或连接失败不能证明任何成员死了，
此时保留组织/成员记录，暂缓 respawn。正常服务恢复后，再由适配器在启动 settle 后逐层修复。

三条规则，都是这个工作流的形状决定的：

1. **每个成员只修自己那一层**。平台只允许直接父重发自己直接子的 token，所以恢复必然逐层发生；
   指望根把整棵树拉起来是做不到的。
2. **先看 pane 里有没有它，再决定做什么**。pane 是唯一的“在跑”证据；已经在跑的**不重启**，只通知它去修自己的子；
   没在跑的先打开 session，等它连上再通知。心跳只是事实，不判死。重开一个跑着的，等于两个人抢同一份队列。
3. **把人排除在外**。`pg_terminate` 过的一律不自动拉起——否则"终止"变成"稍后再启动"。

**这不是"重建"。** 成员的 id、名字、父、会话都不变，回来之后接着用老对话。新建成员是另一件事。

## 5. 适合与不适合

| 适合 | 为什么 |
|---|---|
| 一件事要拆成几块、且需要**一个人负责汇总** | 层级就是汇总结构 |
| 工作要跑很久，超过单个 session 的上下文 | 成员各自持有自己的 session |
| 需要**留下可查的对话记录**：谁跟谁说了什么 | 平台存全部消息 |
| 需要**跨分支横向对账**（A 的子直接问 B 的子） | 一对一不受树约束 |
| 中途会有人介入：追加要求、换人、叫停 | 人能读全部、能发指令 |
| 同一批人反复接活 | 团队持久 |

| 不适合 | 为什么 |
|---|---|
| 单次问答、一次性的小改 | subagent 更便宜，不需要组织 |
| 要求毫秒级反应的控制回路 | 平台的投递是秒级的轮询 |
| 靠共享文件协作 | 平台没有共享空间；同一 cwd 的两个成员会互相覆盖 |
| 需要细粒度权限（"这个成员只能读某些文件"） | 没有权限系统，只有组织形态 |
| 需要广播 | **平台上没有广播**：要通知 N 个人，就发 N 个一对一，或者在他们共同所在的群里说一句 |

## 6. 这些工作流要求适配器提供什么

| # | 能力 | 服务于 | 关键约束 |
|---|---|---|---|
| **F0** | **发现**：列出存活名册（id、名字、父、最后活跃），可按名字找 | 4.6 4.7 | 平台的名册对全员可见，`GET /v1/tree` 就够了。**没有 F0，`pg_say` 只能回复，不能发起** |
| F1 | **入会**：拿 token+URL 认领身份，把简报注入上下文；或者，一个还没有身份的**根候选**会话自己开一个组织（`pg_org_start`） | 4.1 | 简报只注入一次；重启不重复。开组织只在无身份会话里存在 |
| F2 | **持续收**：不依赖"空闲"地轮询；分类后注入 | 4.1 4.4 | 卡死的成员也必须能收到"叫停" |
| F3 | **说话**：发群聊、发一对一（**对任何人，不受树约束**）；发出去就清掉对应的欠回复 | 4.1 4.4 4.6 | 说话与 `pg_ack` 都算"关闭任务"，后者不留消息 |
| F4 | **组织操作**：派生（可带 pi 启动参数）、级联删除、查看下级状态 | 4.1 4.5 | 派生**重试安全**（§9 D5）；**派生立刻返回**——就绪由后台盯（D1），失败以一行 `[spawn]` 通知父，不阻塞调用 |
| F5 | **打断与引导**：cut 当前回合 / 注入一条新方向 | 4.3 | 有界；不注入"你被打断了"之类的提示 |
| F6 | **欠回复**：flag 由投递置起、落盘；到空闲就催，催不动就上报 `blocked`；接收方可用 `pg_ack` 静默结清 | 4.1 4.4 | flag 落盘、重启不清；**对端已死不算欠** |
| F7 | **遥测**：四态、边沿触发、只向上一级、上级侧合并 | 4.3 | 不许替成员报"做完了" |
| F8 | **不丢消息**：取走即消费，所以注入前先落盘，重启重放 | 4.1 | 水位只在投递后推进 |
| F9 | **可停止**：被删时先切断当前回合，再关停，再关 pane | 4.3 4.5 | 关 pane 是最后的硬手段 |
| F10 | **成员间隔离**：journal、水位、pane 映射按成员分 | 全部 | 父子共用目录时必须分 |
| F11 | **诊断**：我是谁、上级是谁、我在忙什么 | 全部 | 给人看的，不是给模型决策的 |
| **F12** | **定时唤醒**：成员可以预约"N 秒后叫醒我，附一句话" | 4.1 4.3 | 一次性、有上限、只在进程内有效。**不是周期轮询**——重复预约是坏味道 |
| **F13** | **重启之后接回来**：进程没了但成员还在时，用记录里的 session 文件与 token 把它重新打开、恢复平台绑定，并让每个回来的成员对**它自己的**下一层做同一件事 | 4.8 | **成员 id 不变**；被删的（`gone`）不可复原；`intent:terminated` 的不拉起；pane 是唯一“在跑”证据；启动自动、运行时手动 |

**不提供的**：权限校验（那是平台的）、内容相关性判断、跨层遥测汇总、界面、重试退避、广播
（平台没有这个概念，适配器也不该假装有）。

## 7. 工具面

模型能看到的只有工具。**每一项 F\* 必须落到一个具体的工具上，否则它不存在。**

| 工具 | 做什么 | 服务于 | 依赖哪一层 |
|---|---|---|---|
| `pg_org_start(name?, port?, data_dir?, platform_dir?)` | **开组织**：找平台代码、必要时拉起平台、bootstrap 出根；`port` 是初始候选，随后消费并跟随平台持久化的实际 URL/port；幂等，已有身份匹配且正常就绪的组织则重接 | F1 | 平台（endpoint、`GET /v1/health`、`POST /v1/bootstrap`）+ 进程（detached） |
| `pg_members(query?)` | **名册**：存活成员及其与我的关系，可按名字过滤（§7.1） | F0 | 平台（`GET /v1/tree`） |
| `pg_say(to, text, mentions?)` | 说话：群、一对一（**任何人都可以**） | F3 | 平台（`POST /v1/messages`） |
| `pg_ack(conv, seq?, all?)` | **清掉一个会话的欠回复通知，不发任何消息**（设计说明 §4.3） | F3 F8 | 适配器（本地账本） |
| `pg_read(to, before?, limit?)` | 读某个会话的历史 | F2 | 平台（`GET /v1/messages`） |
| `pg_spawn(name?, brief, cwd?, args?)` | 派生下级并把它拉起来 | F4 | 平台（建成员、发简报、**就绪判据**）+ herdr（起 pane） |
| `pg_terminate(member)` | 级联删除子树（含 pane） | F4 F9 | 平台（`DELETE`）+ herdr（关 pane） |
| `pg_children()` | 我的下级现在什么状态（遥测快照） | F4 F7 | 适配器自己的遥测表 |
| `pg_inspect(member)` | 主动问某个成员"你在忙什么" | F7 F11 | 平台（指令 + 等回执） |
| `pg_whoami()` | 我的身份、上级、适配器版本、我的状态 | F11 | 平台（`GET /v1/whoami`）+ 适配器 |
| `pg_abort(member)` | 叫停某个成员的当前回合（切断，不携带任何话） | F5 | 平台（指令）+ `PiSurface.abort` |
| `pg_schedule(after_seconds, note)` | 预约一次唤醒：N 秒后把 `note` 投给我并起一轮 | F12 | 适配器（进程内定时器） |
| `pg_respawn()` | 把自己这一层掉线的子成员重新拉起并恢复它们的平台绑定，再让每个回来的成员对**它自己的**下一层做同一件事。无参数：调用者的树位置决定范围 | F1 F4 | 平台（`GET /v1/members/:id`，**只用记录里的旧 token，绝不重发**）+ herdr（`pi --session`，pane 是唯一“在跑”证据）+ 本地记录 |

**`pg_org_start` 是唯一一个"只在会话还没有身份时注册"的工具。** 启动时就有身份的会话
（`PIGROUPS_URL` + `PIGROUPS_TOKEN`）里根本不注册它：否则一个成员就有能力再开一个平台，
用同一个身份去拉两份队列，或者把原来的组织留在没有会话可达的地方。它成功之后才注册其余
十二个工具；**同一个会话里它不会被撤销**（pi 没有注销工具的接口），再调只回答
`already_member`，不重建会话、不启动第二个平台。失败则停掉自己刚起的平台，不留下孤儿进程。

**没有 `pg_steer` 这个工具。** "改方向"就是 `pg_say`——平台里没有一种"说话"自带强制力。
而"停下来"是 `pg_abort`，它不携带任何话：切断是运维动作（§7.2），指引是沟通动作。

**为什么成员工具是十二个而不是更少**：少一个，就有工作流要靠"模型自己记得"。去掉 `pg_members`，
`pg_say` 就只能回复已有对话——**平台的"任意两人可私聊"这条能力在工具面上不存在**。
去掉 `pg_respawn`，**机器重启之后就没人能把组织接回来**——平台里的成员还在，但没人知道各自的 session 文件与 token（设计说明 §12）。
去掉 `pg_ack`，**"这个线程结束、我不回了"就无法表达**：只能用 `pg_say` 发一句“不用回了”，
而那一句本身又给对方置一次债（设计说明 §4.1）。2026-11-03 的实测就是这个循环：17 次 ack↔ack 往返、
14 次撞上催办上限。

**为什么不再多**：每多一个工具，模型的工具选择空间就大一档。**新增门槛是"某条工作流没有它
就走不通"，不是"有它方便"。** `pg_org_start` 不算在这十二个里：它不是成员能力，是进门那一步，
而且只在还没有身份时存在。

### 7.1 名册的契约

```
pg_members({ query?: string })
→ { self, total, matched, members: [
      { id, name, parent_id, parent_name,
        relation: "self" | "parent" | "child" | "sibling" | "peer",
        child_count, last_seen_at }
  ] }
```

三个决定各有其因：

**① `query` 只按名字做大小写不敏感的子串匹配。** 不按 id 搜——**id 是不透明的**（`m_635f7e`），
没人猜得出，也没人记得住。名字是人唯一的把手。

**① bis 还返回 `self`**——调用者自己的 id，让"这条是我"可以直接比对，不必再问一次 `pg_whoami`。

**② 返回 `total` 和 `matched`。** 没有这两个数，`matched: 0` 会被模型读成"不存在这个人"，
而实际只是**名字打错了**。有 `total: 23, matched: 0`，它就知道是筛错了，可以不带 query 再列一次。

**③ 每个人都带 `relation`。** 这是本设计里最不显然的一条：**平台允许给任何人发消息，
但只有 `child` 能被 `pg_abort`**（§7.2）。如果名册只给 id 和名字，模型会对一个
`peer` 调 `pg_abort`，被拒之后才开始猜"为什么"。把关系直接写进结果，是让能力边界**在数据里
可见**，而不是靠模型记住文档。

`parent_name` 同理：不给它，模型要为每个名字再查一次父是谁，而"我该找他还是找他的上级"
恰恰取决于这条边。

**为什么名册是独立工具而不是把 `pg_whoami` 撑大**：一个回答"我是谁"，一个回答"还有谁"；
用途不同（诊断 vs 找人），数据量差一个数量级。混在一起会让每次诊断都拖着整棵树。

### 7.2 剩下的那一条指令也只能向下——这是适配器的规矩，不是平台的

平台只校验"两人同群"。父与子天然同群，`sharesGroup` 对父子双向为真，所以**平台层面
下级也能给上级发指令**。适配器把它收窄成单向：`pg.abort`（以及线上仍接受的 `pg.steer` 控制项）
只认**直接上级**或人。

这条收窄是有意的：指挥权是组织的方向性，不是连通性。

### 7.3 `pg_spawn` 的参数只有一个特殊：`args`

`args` 是**原样追加到 pi 命令行**的字符串数组，不校验、不改写。

理由：pi 有四十多个启动参数，任何"镜像常用参数"的 schema 都会立刻落后。**契约是 pi 的，
不是我们的**——模型要查就跑一次 `pi --help`。

这也意味着**调用方可以用 `args` 改变下级的启动语义**（`-p` 让它跑完就退、`--tools read`
限制它能用的工具）。这不是 bug，是调用方的选择。

### 7.4 为什么"开组织"不是"注册成员"

因为**成员仍然不能给自己注册**。但在 v0.6 之前，连根也只能由人手工创建：人起平台、
`POST /v1/bootstrap`、再把 URL 和 token 塞进环境变量启动 pi。一个装着 skill 却没有工具的
会话因此只能安静地退回 subagent。

现在多一条路径：**一个还没有身份的会话可以用 `pg_org_start` 给自己开一个组织，自己当根。**

| 谁做的 | 动作 | 凭据 |
|---|---|---|
| 还没有身份的会话（根候选） | `pg_org_start`：找平台代码 → 必要时起平台 → `POST /v1/bootstrap` → 成为根 | 无（新平台的第一个成员） |
| 人 | 调试或接管时手工做一遍：起平台、`POST /v1/bootstrap`、带两个环境变量启动 pi（不是必需路径） | bootstrap 本身不需要鉴权；管理员 token（环境变量）只用于建人 |
| 成员 | `pg_spawn`（内部就是 `POST /v1/members`） | 自己的 token |

三条路径的区别是**谁先存在**：根候选会话先造出平台；人可以在平台已经存在时手工引导；
成员永远是被别人创建的。`pg_org_start` 不给成员“再注册一个我”的能力——它在启动时就有身份
的会话里根本不注册；根自己开出来的那个会话里它仍留着（pi 不能注销工具），但再调只回答
`already_member`，不会造第二个平台。所以“注册”在成员工具面上仍然只表现为
**`pg_spawn` 这一个工具**。

这条也解释了两个部署事实：

- **普通成员的凭据仍然是启动参数，不是它能调用的接口**。所以 token 泄露在架构上等价于
  "这个成员被顶替"，适配器无法自证身份。
- **根的凭据落在本机文件里**：`<adapterDir>/orgs/<key>/org.json`（0600）。它不是"平台发了一张通行证"，
  而是"这个会话在这台机器上创建了平台"的记录；下一次会话靠它重接，而不是重新开一个。

一次开组织的实际顺序（平台 0.7.0 起，见设计说明 §8.2）：

```
会话（无身份）
  └─ 只有 pg_org_start
       ├─ 读 <adapterDir>/orgs/<key>/org.json 与 platforms/<id>/endpoint.json：
       │   同身份、health 就绪且凭据有效 → 重接，结束
       ├─ 找平台代码（platform_dir → PIGROUPS_PLATFORM_DIR → ../PiGroups → ../../PiGroups）
       ├─ node <platform>/src/main.ts（detached；PORT 只是第一候选）
       ├─ 平台用 endpoint.json 的 wx claim 会合 → bind 端口 → 改写 endpoint → 打开库；
       │   绑定失败时探测两次身份；没有 .start.lock
       │   ├─ 同 platform_id → 退出码 2（另一端在服务）→ 重读 endpoint 并重接
       │   └─ 另有服务 / 无人应答 → 平台换下一个端口；端口不可用才失败，适配器只跟随结果
       ├─ 跟随 endpoint，等正常 GET /v1/health；启动期身份不代表服务已就绪
       ├─ 新组织才 POST /v1/bootstrap {name}
       └─ 原子更新已验证 URL 到 org.json → 注册其余十二个工具 → 开始轮询
```

关键性质：平台在会话退出后还在；第二次调用按同一平台身份重接；失败只清理本次负责的进程，
不会因 health 暂不可达杀既有实例。`org.json` 保存根凭据与组织关联，平台 endpoint 保存当前服务地址，
两者职责不同：端口只回答"这个平台是否已经有一个进程在服务"，不承担 agent 判活、唤醒或 respawn。
端口通常不变；确实前进时，已经在跑的成员手里还是旧地址，要重开才会拿到新的（设计说明 §8.2）。

### 7.5 `pg_schedule` 为什么值得成为工具

没有它的时候，一个成员要在"过一会儿再看"这件事上只有两条路，两条都差：

| 做法 | 问题 |
|---|---|
| 在一个回合里 `bash sleep 600` | 回合一直开着：上级的遥测看到的是 **working**（它其实在睡），期间到达的消息只能排队或 steer 进来，**成员不响应** |
| 结束回合，指望别人来叫 | 没有消息就没有唤醒——"10 分钟后看 CI"这件事**永远不会发生** |

`pg_schedule` 把这件事变成：**成员回到 idle（可以随时响应），到点由适配器投一条消息并起一轮**。

边界写清楚，否则它会退化成轮询：

- **一次性**：到点触发一次，不重复。
- **上限**：待触发的预约数有上限（设计稿定具体数），超过就拒绝——拒绝比静默丢弃好。
- **只在进程内**：适配器重启，预约全部消失。**这是有意的**：落盘会让"上次那个意图还该不该执行"变成一个新问题，而没人能回答它。
- **不是周期任务**：连续预约同一个 note 是坏味道，说明该用遥测或该让上级盯着。
- 投递时带 `[scheduled]` 前缀，模型能分清"这是谁叫醒我的"。

### 7.6 是否还需要 skill

**需要。** 工具解决"能做什么"，skill 解决"该怎么用"。三件事工具说不清：

1. **什么时候该说话**——工具只执行"说"，判断"该不该说"是判断力
2. **怎么简报**（对上级而言）——一份坏简报会让下级反复来问
3. **卡住时怎么办**——先说清楚再等，还是直接升级

| skill | 给谁 | 内容 |
|---|---|---|
| `pigroups-message` | 每个成员 | 任务由消息或 `pg_ack` 关闭；`pg_say` 的 `to` 要写群 `g:<owner>` 或**裸成员 id**（`dm:…` 只是读侧的会话 id）；点名只在本群有效；一对一发给谁都可以；不要轮询平台 |
| `pigroups-org` | 每个成员（尤其是根） | 根的第一件事是用 `pg_org_start` 把组织开起来并给它起名；怎么写一份不需要再问的简报；怎么看遥测与最后一轮；什么时候 `pg_inspect`、什么时候 `pg_abort`、什么时候 `pg_terminate`；成员按"它负责什么"命名——名册只能按名字搜 |

不放进 skill 的：机械保证（落盘、重放、欠回复）——那些在代码里，**提示词只负责减少触发**。

## 8. 入站的东西怎么进上下文

进上下文的有六个来源：**聊天消息、指令（执行类）、子成员状态、适配器自己（催办/预约/简报）、
平台的 gap 信号**。判据是**这条东西是谁的事实、给谁用**。

三条原理：

1. **给循环执行的东西永远不进上下文。** 模型不需要知道自己被体检了，也不需要读"系统正在切断你"。
2. **进上下文的东西必须自带三样：身份、出处、种类。** `details.kind` 只活在 UI 里，
   **不进模型的上下文**，所以只能靠正文前缀区分。
3. **打断是显式动作，不是流量的副作用。**

### 8.1 投递：一条队列 + 时间窗 + steer

- **一条队列**：所有要进上下文的东西进同一个队列，每项带来源、身份、到达时间。
- **翻滚时间窗**（默认 60 秒）：第一条 `windowed` 项到达时开窗，窗口关闭后整批投出去；
  之后的消息开下一个窗。**按时间，不按条数**——条数上限只能是安全阀，绝不能是触发器。
- **投递用 pi 的 `steer`**：不等空闲。空闲时会直接起一轮；忙时插进当前这一轮的下一个模型调用。
- **没有 `isBusy()` 闸门，也没有"一次 settle 只投一次"**——这两条是旧设计的产物，随 steer 一起删掉。
- **溢出**：一次投递最多 10 条，多出来的**重开一个窗**等下一轮，绝不因为没凑够而不投。
- **重放**（重启后的 journal）也要过窗口——最坏情况下重启后要等一个窗口才补上。

理由是最朴素的：**一个 agent 干活时收到新要求，本来就是正常工作状态。**

### 8.2 测量的边界（2026-11-01，`probe/logs/steer-20261101T170244Z/`）

`steer` 的"下一个模型调用"是**字面意思**：

| 场景 | 发送 | 工具返回 | 标记落盘 | 模型首次提到 |
|---|---|---|---|---|
| 长工具 60s | 54.999 | 49.880（+55s） | **+1ms** | +0.6s |
| 短工具 5s | 58.435 | 01.772（+3s） | **+1ms** | +0.8s |

**`sendMessage` 返回 = 排队，不是被看到。** 一个成员卡在 60 秒的工具里，steer 也要等 60 秒。
所以投递延迟 = **窗口剩余时间 + 当前工具剩余时间**，不是"最多 60 秒"。

**这条改变了 abort 的地位**：要在一个长工具期间改变它的行为，`say` 做不到——只有 `pg_abort` 能做到。
这就是 `pg_abort` 留在工具面上的理由。

### 8.3 abort 与投递的竞态（同一个实验）

| 顺序 | 结果 |
|---|---|
| **say（native steer 排队中）→ abort** | **消息彻底丢失**：整份 session 文件里 0 次出现，之后的回合也再没出现 |
| **abort → say** | 消息落进 transcript（`custom_message`），下一个提示就能看到（虽然那一轮已被切断） |

所以有两条硬规矩：

**① `abort` 之后立刻关窗投递。** 窗口存在的理由是"别打断正在干的活"；abort 已经把活停了，
窗口的理由随之消失。实现上要两个状态才做得到：一次"强制立刻投"（把已攒的投掉），
再加一个"下一批免等窗口"的标记（abort 之后才到的消息，也就是"先 abort 再 say"里那个 say）。

**② 投递出去但还没被确认的批次，要留一份副本；那一轮以 aborted 结束时重新入队。**
"pi 收下了"不是"模型看到了"——这正是 D2 缺口在投递层的表现。副本留在内存里即可：
崩溃丢失副本的代价是"可能少一次重投"，而重复注入有 `[会话#序号]` 兜住。

### 8.4 各类的来源与形态

| 来源 | 时机 | 合并 | 形态 |
|---|---|---|---|
| 聊天消息 | 窗口关闭 | 是 | `[会话#序号] 名字: 正文` |
| 指令 · `pg.abort` / `pg.inspect` | 立即，由循环执行 | 否 | **不进上下文** |
| 指令 · 未知 / `v>1` | 窗口关闭 | 与消息同批 | `[control 来自 id] cmd payload` |
| 子成员状态 | 合并窗口到期，且窗口关闭后；**同一状态的进入只提醒一次**（要持续盯就去读 `pg_children`） | 是 | `[下级] 谁、什么状态、跑多久、最后一轮在做什么`。六态：`stalled` `slow_turn` `error` `idle_owed` `blocked` `silent_acking`；**`idle_owed` 上报但不进汇总**（父级付不掉） |
| 适配器的催办 | 队列空时**由催办自己开一个窗**，攒到窗口关闭再投 | 是 | `Unanswered messages: <会话> #<序号>. Reply, or call pg_ack to clear this notification.` |
| 预约唤醒 | **到点后仍要等窗口**（实测：10 秒的预约晚到 8.9 秒） | 单条 | `[scheduled] note` |
| 启动简报 | 启动，**不等窗口** | 否 | `[dm#序号] 父: 正文` |

**子→父只有 `pg.attention` 一种通知。** 早先还有一个 `pg.report`（设计上装“成员的结论”：`done`/`progress`/`blocked`），
但它从来没有对应的工具——成员汇报一直走 `pg_say`——而实际用到它的只有两件适配器**替**成员说的话：
“催满三次没人应”与“我要退出了”。两件都有进入/离开，因此并进 attention 的两个状态。
理由是： **状态可以合并、可以被取消（“全部 recovered 就静默取消”），而结论不行**。一条结论塞进状态通道会被静默取消；
一条“已经报了、不会有后续”的通知塞进状态表，就会变成一个永远关不掉的行——那正是 6.5 小时重播的成因。

### 8.5 父要看得到子“最后一轮在做什么”

没有这条，`pg_abort` 是一次盲操作。所以子成员的 attention 上报里要带**最后一轮的概要**：
最后一条助手文本（截断）和最后一个工具调用（名字、参数预览、成功与否）。

**这一条要扩 `PiSurface`**：现在的事件只有 `turn_start / tool_start / tool_end / turn_end`，
拿不到助手正文；pi 本身有 `message_end`，要把它接进 `PiSurface` 并保留最后一条助手文本。

## 9. 派生事实的定义

适配器有六个"事实"是它自己造的，不是任何一层的。**它们必须逐个写清定义**，否则会在实现里
被别人的词表悄悄替换掉（§10 就是这样出的错）。

| 派生事实 | 定义 | 谁的话算数 |
|---|---|---|
| **D1 成员就绪** | 那个成员的适配器**已经连上平台**：`last_seen_at` 非空（⇒ URL 对、token 对、轮询活着） | **平台，唯一判据**。herdr 的界面状态不能用来判就绪——它已错过两次（`done` 不是 `idle`；拿到长简报的子成员立刻是 `working`）。herdr 只在超时时用来分辨「进程没起来」与「起来了但连不上平台」 |
| **D2 消息已投递** | pi **接受了**这条消息（排队） | **pi**。**不保证模型看到了**——实验证明长工具期间 steer 要等工具返回才被看到，而 steer 后 abort 会整条丢失。**不收紧、不做已读**：这与"平台不维护已读"是同一个决定（§11） |
| **D3 回合结束** | pi 的 `agent_before_settle`，或（被 abort 时）`agent_settled.aborted` | **pi** |
| **D4 工具被切断** | 那一轮是我们主动 abort 的，且工具在返回前被切断 | **适配器**（pi 的 `isError` 在切断时是 `false`，**不能拿它当"成功"**） |
| **D5 派生的幂等** | 同一个父、同一个名字，重试**不产生第二个成员** | **平台**（幂等键是 `(parent_id, request_id)`，所以 `request_id` 必须由 `(父, 名字)` 确定性派生） |
| **D6 可达 ≠ 该发** | 平台允许给任何成员发一对一；**发不发是判断**，不是能力 | **平台**给能力，**skill 给判断** |

D1 和 D4 各自对应一个真实缺陷：D1 曾用 herdr 的 `idle/done` 当就绪（健康的子成员被报"派生失败"）；
D4 曾把 `isError:false` 当成功（"被切断的工具"被报成"工具成功"）。

D5 是一条**新承诺**：它让"派生失败后重试"从危险动作变成安全动作。就绪判断以后再出错，
也只会慢，不会多出一个人。

## 10. 一个真实的架构错误（反面教材）

实现里曾经这样做"派生是否成功"：

```
派生子成员 → herdr agent wait <pane> --until idle → 成功
```

真机对照（同一个 pi，只改一个参数）：

| 状态 | 命令 | 结果 |
|---|---|---|
| 还没跑过一轮 | `--until idle` | 成功 |
| **跑完一轮之后**（herdr 报 `done`） | `--until idle` | **超时失败** |
| 跑完一轮之后 | `--until done` | 成功 |

子成员拿到简报就开始干活——**这是正常情况**，于是每次派生白等 120 秒，并把
`timed out waiting for agent status` 当错误交给上级。上级看到失败最可能做的事是**重试**，
重试又造出重复成员。

**错在哪：**把 herdr 的界面状态当成了"成员就绪"。`done` 是 herdr 对自己 UI 的说法，
不是"这个成员准备好接活了"。而"准备好了"的证据**一直在我们自己的协议里**：子成员的适配器
一旦连上平台，平台就会在鉴权时刷新 `last_seen_at`。

同一个错误的第二种形态（v2.1 才发现的）：**把"层级"当成了平台的寻址模型**，于是漏掉
"任意两人可私聊"这条能力，也漏掉了承载它的名册工具。**能力在平台里存在，在工具面上不存在**——
这种缺失不会报错，只会让某些工作流悄悄走不通。

## 11. 它不做什么

| 不做 | 原因 |
|---|---|
| 命令白名单 / 拦截危险命令 | 不属于这个插件；执行环境该管的事 |
| 自己的重试退避 | pi 已经重试了，两套退避会打架 |
| 相关性分类器（这条消息要不要理） | 平台的 `mentions_me` / `from_parent` / `dm:` 已经够用 |
| 跨层遥测汇总 | 只向上一级；人是兜底 |
| 界面 | 界面是平台上另一个消费者 |
| 改平台 | 平台只按 token 和 HTTP 交互，适配器不该要求它多懂一点 |
| 给成员加权限 | 没有权限系统，只有组织形态 |
| 广播 | 平台没有广播；要通知多人就发多个一对一，或在共同群里说一句 |
| 复活被删掉的成员 | 平台连 token 都不肯给 `gone` 的成员重发；身份不能凭空造，只能新建——那是 `pg_spawn`，不是复活 |
| 自动拉起 `pg_terminate` 过的成员 | 否则"终止"只是"稍后再启动"；要它回来就显式 `pg_spawn` |

## 12. 五个必须成立、但不显然的判断

**① 拉到的消息要先落盘再注入。**
平台的投递是取走即消费。取走之后、注入之前崩掉，那条消息就永远消失，而且没人会发现。

**② 注入文本要带消息号。**
重放可能重复注入。编号写进文本（`[g:m_abc#89]`），模型能自己认出"这条我处理过"。

**③ 一个成员一个进程。**
适配器用 `consumers/<sha1(token)>.json` 的消费者租约挡住第二个 pane（pid + `/proc` 启动时间）；
它不注册工具、不 poll、不心跳。平台对同一成员的并发 `poll` 回 409 只是第二道保险。
同一个身份被两个进程驱动，两条投递流会互相偷消息。

**④ 派生出来的成员是正常的 agent，不是被剥光的执行器。**
它有操作者的工具、skill、MCP、上下文文件——和一个人在这个 pane 里敲 `pi` 得到的完全一样。
把它当成一次性的 worker 是错的：**团队要能长期存在，成员就得是一个完整的 agent。**

**⑤ herdr 只对"带队伍的成员"必需。**
`pg_spawn` / `pg_terminate` 的实现依赖 herdr；一个不派生的成员完全可以由人手工起一个
`pi` 然后在里面干活——它照样是一个合法成员。所以 herdr 是**领导角色的依赖**，不是成员的门槛。

## 13. 待审问题

1. **两个 skill 的边界**：`pigroups-org`（组织管理）与 `pigroups-message`（消息通知）怎么切
   干净——比如"什么时候该 abort"属于组织，而"怎么回一条消息"属于消息，但两者在真实任务里
   是交织的。倾向：**按工具归属切，不按场景切**；场景 skill 由使用者自己写。
2. **`pg_schedule` 的上限与最长预约**：设计稿要定待触发条数与单次最长。
   倾向：8 条 / 最长 24 小时 / 下限 5 秒（= tick 粒度）。
3. **窗口长度是否可配**：默认 60 秒。它和长 poll（25 秒）的关系要写清——窗口至少要覆盖两次
   poll，否则一个窗口内可能收不到完整的一批。倾向：可配，默认 60。
4. **`pg_inspect` 能不能问非下级**：平台的指令通道只允许同群。所以问同级会失败。
   倾向：工具描述里写清"通常只能问直接下级"，失败时把平台的原话返回给模型。
5. **末轮概要的截断长度**：助手正文与工具参数各留多少字。倾向：正文 500、参数 200（与现有
   预览一致）。
