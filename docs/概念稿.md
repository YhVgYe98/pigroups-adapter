# PiGroups Pi 适配器 概念稿

> 版本：v2.0（待审）
> 平台侧的权威文档在 `../PiGroups/docs/`。本文只讲**适配器**。
> v1 讲的是"为什么要它"；v2 补上 v1 缺的四件事：**它服务什么工作流、这些工作流要什么能力、
> 这些能力对应哪些工具、每个工具该信谁的话**。v2 修掉了一个 v1 里没有、但实现中真实发生的
> 架构错误（见 §8）。

---

## 1. 它是什么

一个装在 pi 里的扩展。装进去之后，那个 pi session 就**成为一个组织的成员**：有身份、在群里说话、
能拉起下级、能被上级叫停、能被人看见。

一句话的定位：

> **它把"一群 pi 会话"变成"一个有层级的团队"。**

平台那一侧刻意什么都不懂——不懂 agent 是什么、由谁拉起、如何唤醒、死没死。**所有这些都落在这里。**

---

## 2. 三层的职责，以及适配器站在哪

这套系统里有三个别人写的组件，和一个我们写的。**分清谁拥有哪个事实，是这个仓库最重要的一条纪律。**

| | 拥有什么 | 不拥有什么 |
|---|---|---|
| **PiGroups 平台** | 组织：成员树、名字、token、alive/gone；会话与消息（每会话序号、取走即消费、gap）；不透明指令；投递回执；`last_seen_at` | 回合、工具、进程、pane、模型、相关性、紧急程度。**它不知道 agent 是什么** |
| **pi** | 会话：一轮回合的开始与结束、消息是否被接受、工具是否在执行、`isError`、session 文件 | 这条消息对 PiGroups 意味着什么 |
| **herdr** | 终端与进程：pane/tab、某个 pane 里跑着什么、按键回显、滚动缓冲；**以及它为自己界面推断的 `agent_status`**（启发式，不是协议） | 那个 pi 是不是一个成员、它有没有连上平台、它准备好没有 |
| **适配器** | 三者之间的**全部跨层语义**：成员就绪、已投递、完成、被切断、欠回复、卡住；journal、水位、义务、遥测、pane 映射、催办策略 | 组织本身（平台的）、回合内容（pi 的）、进程（herdr 的） |

由此得出贯穿全文的一条规则：

> **每个事实只能从它的拥有者那里取。适配器可以"派生"事实，但派生必须写明推导方式，并且知道它不等于原事实。**

违反这条会产生**看起来像性能问题、实际是语义错误**的故障。§8 是一个真实的例子。

## 3. 它服务什么工作流

适配器不是"帮我跑一个子任务"的工具。**一次性子任务用 subagent 更便宜**——那是同一个进程里的
派生，没有身份、没有组织、任务结束就消失。

适配器服务的是**需要组织的事情**。可以形成的五条工作流：

### 3.1 派活—汇报（最基本的一条）

```
人 ──任务──▶ 根成员 ──pg_spawn + 简报──▶ 子成员 A / B / C
                    ◀──pg_say（结论）──────┘
                    ──汇总──▶ 人
```

要点：**任务由消息开具，也由消息关闭。** 上级不靠"进程还活着"判断进度，靠下级开口。

### 3.2 持续值班（长期团队）

同一个组织长期存在，接一批又一批任务。成员保留自己的 session，所以**上下文是连续的**：
上一个任务的结论、踩过的坑，下一个任务还能用。这是 subagent 做不到的。

### 3.3 卡住处理（不确定性落到具体人）

某个成员卡在工具里、某个回合带着错误结束、某个成员半天不说话。
上级看到遥测 → 判断 → `pg_abort`（切断）或 `pg_steer`（换方向）或 `pg_terminate`（换人）。

### 3.4 升级（下级遇到越权的事）

下级需要拍板，但决定超出它的范围：`pg_say` 给上级，等回复。**等待本身不消耗回合**——
它只是欠一条回复，而欠回复由适配器盯着。

### 3.5 组织变更

活多了一个人干不完 → `pg_spawn`；某个分支没有存在的必要 → `pg_terminate`（级联删子树）。
组织是**活的**，不是启动时定死的。

## 4. 适合与不适合

| 适合 | 为什么 |
|---|---|
| 一件事要拆成几块、且需要**一个人负责汇总** | 层级就是汇总结构 |
| 工作要跑很久，超过单个 session 的上下文 | 成员各自持有自己的 session |
| 需要**留下可查的对话记录**：谁跟谁说了什么 | 平台存全部消息 |
| 中途会有人介入：追加要求、换人、叫停 | 人能读全部、能发指令 |
| 同一批人反复接活 | 团队持久 |

| 不适合 | 为什么 |
|---|---|
| 单次问答、一次性的小改 | subagent 更便宜，不需要组织 |
| 要求毫秒级反应的控制回路 | 平台的投递是秒级的轮询 |
| 靠共享文件协作 | 平台没有共享空间；同一 cwd 的两个成员会互相覆盖 |
| 需要细粒度权限（"这个成员只能读某些文件"） | 没有权限系统，只有组织形态 |

## 5. 这些工作流要求适配器提供什么

从 §3 反推，功能清单（编号供设计稿引用）：

| # | 能力 | 服务于 | 关键约束 |
|---|---|---|---|
| F1 | **入会**：拿 token+URL 认领身份，把简报注入上下文 | 3.1 | 简报只注入一次；重启不重复 |
| F2 | **持续收**：不依赖"空闲"地轮询；分类后注入 | 3.1 3.4 | 卡死的成员也必须能收到"叫停" |
| F3 | **说话**：发群聊/私聊；发出去就清掉对应的欠回复 | 3.1 3.4 | 只有说话算"关闭任务" |
| F4 | **组织操作**：派生（可带 pi 启动参数）、级联删除、查看下级状态 | 3.1 3.5 | 派生**重试安全**（见 §7 的 D5） |
| F5 | **打断与引导**：cut 当前回合 / 注入一条新方向 | 3.3 | 有界；不注入"你被打断了"之类的提示 |
| F6 | **欠回复**：从历史算出来，到空闲就催，催不动就上报 `blocked` | 3.1 3.4 | 不存本地状态；对端已死不算欠 |
| F7 | **遥测**：四态、边沿触发、只向上一级、上级侧合并 | 3.3 | 不许替成员报"做完了" |
| F8 | **不丢消息**：取走即消费，所以注入前先落盘，重启重放 | 3.1 | 水位只在投递后推进 |
| F9 | **可停止**：被删时先切断当前回合，再关停，再关 pane | 3.3 3.5 | 关 pane 是最后的硬手段 |
| F10 | **成员间隔离**：journal、水位、pane 映射按成员分 | 全部 | 父子共用目录时必须分 |
| F11 | **诊断**：我是谁、上级是谁、我在忙什么 | 全部 | 给人看的，不是给模型决策的 |

**不提供的**：权限校验、内容相关性判断、跨层遥测汇总、界面、重试退避。

## 6. 工具面

模型能看到的只有工具。所以**每一项 F\* 必须落到一个具体的工具上**，否则它不存在。

| 工具 | 做什么 | 服务于 |
|---|---|---|
| `pg_say(to, text, mentions?)` | 说话：群、私聊、上级 | F3 |
| `pg_read(to, before?, limit?)` | 读某个会话的历史（上下文） | F2 |
| `pg_spawn(name?, brief, cwd?, args?)` | 派生一个下级成员，并把它拉起来 | F4 |
| `pg_terminate(member)` | 级联删除子树（含 pane） | F4 F9 |
| `pg_children()` | 我的下级现在什么状态（遥测快照） | F4 F7 |
| `pg_inspect(member)` | 主动问某个下级"你在忙什么" | F7 F11 |
| `pg_whoami()` | 我的身份、上级、适配器版本、我的状态 | F11 |
| `pg_abort(member)` | 叫停某个下级的当前回合 | F5 |
| `pg_steer(member, text)` | 给某个下级换方向 | F5 |

**为什么是九个而不是更少**：少一个就意味着有一条工作流要靠"模型自己记得"。比如去掉 `pg_inspect`，
上级就只能看遥测，无法在下级沉默时主动问一句——而 §3.3 恰恰是"沉默"的处理。

**为什么不再多**：每多一个工具，模型的工具选择空间就大一档，误用概率上升。**新增工具的门槛是
"某条工作流没有它就走不通"**，而不是"有这个会方便"。

### 6.1 `pg_spawn` 的参数只有一个特殊：`args`

`args` 是**原样追加到 pi 命令行**的字符串数组，不校验、不改写。

理由：pi 有四十多个启动参数，任何"镜像常用参数"的 schema 都会立刻落后。**契约是 pi 的，
不是我们的**——模型要查就 `pi --help`。

这也意味着：**调用方可以用 `args` 改变下级的启动语义**（`-p` 让它跑完就退、`--` 让它先吃一段提示）。这不是 bug，是调用方的选择；文档写明即可。

### 6.2 是否还需要 skill

**需要，而且是两个。**

工具解决"能做什么"，skill 解决"该怎么用"。三件事工具说不清：

1. **什么时候该说话**——工具只能执行"说"，判断"该不该说"是判断力
2. **怎么简报**（对上级而言）——一份坏简报会让下级反复来问
3. **卡住时怎么办**——先说清楚再等，还是直接升级

| skill | 给谁 | 内容 |
|---|---|---|
| `pigroups-member` | 每个成员 | 任务由消息关闭；发消息要带会话 id；`pg_*` 各工具的语义与边界；被 abort 后怎么办；不要轮询平台 |
| `pigroups-lead` | 带下级的成员 | 怎么写一份不需要再问的简报；怎么看遥测；什么时候 abort / steer / terminate；什么时候该自己干而不是派 |

不放进 skill 的：机械保证（落盘、重放、欠回复）——那些在代码里，**提示词只负责减少触发**。

## 7. 派生事实的定义（本轮最重要的补充）

适配器有三个"事实"是它自己造的，不是任何一层的。**它们必须逐个写清定义**，否则就会
在实现里被别人的词表悄悄替换掉（§8 就是这样出的错）。

| 派生事实 | 定义 | 谁的话算数 |
|---|---|---|
| **D1 成员就绪** | 那个成员的适配器**已经连上平台**（`last_seen_at` 非空 ⇒ URL 对、token 对、轮询活着）**且** herdr 里那个 pane 有一个 agent 进程 | **平台**（主）＋ herdr（只证明进程起没起） |
| **D2 消息已投递** | pi **接受了**这条消息 | **pi**（`sendMessage` 返回即算）。**不保证起了回合**——这是已知缺口，写进风险表，不假装它是别的 |
| **D3 回合结束** | pi 的 `agent_before_settle`，或（被 abort 时）`agent_settled.aborted` | **pi** |
| **D4 工具被切断** | 那一轮是我们主动 abort 的，且工具在返回前被切断 | **适配器**（pi 的 `isError` 在切断时是 `false`，**不能拿它当"成功"**） |
| **D5 派生的幂等** | 同一个父、同一个名字，重试**不产生第二个成员** | **平台**（幂等键是 `(parent_id, request_id)`，所以 `request_id` 必须由 `(父, 名字)` 确定性派生） |

D1 和 D4 各自对应一个真实缺陷：D1 曾用 herdr 的 `idle/done` 当就绪（结果是健康的子成员被报
"派生失败"）；D4 曾把 `isError:false` 当成功（结果是"被切断的工具"被报成"工具成功"）。

D5 是一条**新的承诺**：它让"派生失败后重试"从危险动作变成安全动作。就绪判断以后再出错，
也只会慢，不会多出一个人。

## 8. 一个真实的架构错误（写下来，因为它是这套设计的反面教材）

实现里曾经这样做"派生是否成功"：

```
派生子成员 → herdr agent wait <pane> --until idle → 成功
```

真机上测到的对照（同一个 pi，只改一个参数）：

| 状态 | 命令 | 结果 |
|---|---|---|
| 还没跑过一轮 | `--until idle` | 成功 |
| **跑完一轮之后**（herdr 报 `done`） | `--until idle` | **超时失败** |
| 跑完一轮之后 | `--until done` | 成功 |

子成员拿到简报就开始干活——**这是正常情况**，于是每一次派生都要白等 120 秒，并把
`timed out waiting for agent status` 当错误交给上级。而上级看到失败最可能做的事是**重试**，
重试又造出重复成员。

**错在哪：**把 herdr 的界面状态当成了"成员就绪"。`done` 是 herdr 对自己 UI 的说法，
不是"这个成员准备好接活了"。而"准备好了"这件事的证据**一直在我们自己的协议里**：
子成员的适配器一旦连上平台，平台就会在鉴权时刷新 `last_seen_at`。

教训成为规则（§2 那条）：
**取事实要找拥有者；派生事实必须写明推导；别人的状态词只有在写明"它还可能是什么意思"之后才能用。**

## 9. 它不做什么

| 不做 | 原因 |
|---|---|
| 命令白名单 / 拦截危险命令 | 不属于这个插件；执行环境该管的事 |
| 自己的重试退避 | pi 已经重试了，两套退避会打架 |
| 相关性分类器（这条消息要不要理） | 平台的 `mentions_me` / `from_parent` / `dm:` 已经够用；门控在小队里是净亏 |
| 跨层遥测汇总 | 只向上一级；人是兜底 |
| 界面 | 界面是平台上另一个消费者 |
| 改平台 | 平台只按 token 和 HTTP 交互，适配器不该要求它多懂一点 |
| 给成员加权限 | 没有权限系统，只有组织形态 |

## 10. 四个必须成立、但不显然的判断

**① 拉到的消息要先落盘再注入。**
平台的投递是取走即消费。取走之后、注入之前崩掉，那条消息就永远消失，而且没人会发现。

**② 注入文本要带消息号。**
重放可能重复注入。编号写进文本（`[g:m_abc#89]`），模型能自己认出"这条我处理过"。

**③ 一个成员一个进程。**
平台对同一成员的并发 `poll` 回 409。这不是限制，是提醒：同一个身份被两个进程驱动，
两条投递流会互相偷消息。

**④ 派生出来的成员是正常的 agent，不是被剥光的执行器。**
它有操作者的工具、skill、MCP、上下文文件——和一个人在这个 pane 里敲 `pi` 得到的完全一样。
把它当成一次性的 worker 是错的：**团队要能长期存在，成员就得是一个完整的 agent。**

## 11. 待审问题

写着写着发现有几处只能由你定，列在这里，不自己拍：

1. **`pg_read` 是否保留**。它有 `pg_say` 的镜像感（能说话就能读历史）。但它让成员不用靠记忆，
   也不依赖平台额外接口。倾向保留。
2. **两个 skill 是否都做**。`pigroups-member` 是必需的；`pigroups-lead` 可能和"领导本质上是
   普通成员 + 多几个工具"重复。倾向先做 member，lead 等真机上观察到坏简报再说。
3. **D2（已投递 ≠ 起了回合）要不要收紧**。收紧需要给 `PiSurface` 加"下一轮 `agent_start` 确认"，
   代价是投递路径变复杂。倾向先不动，写在风险表里。
