# PiGroups Pi 适配器 设计说明

> 版本：v1.0
> 地位：**《概念稿》是权威**，本文是它的实现伴稿。
> 平台侧的接口契约在 `../PiGroups/docs/设计说明.md` §10。本文只补充适配器自己的契约。

---

## 1. 形态

**一个 Pi 扩展包。** 没有守护进程，没有独立进程，没有旁路服务。装进一个 pi session，那个 session 就是成员。

```
src/
  extension.ts   Pi 扩展入口：注册 pg_* 工具、挂事件、构造 PiSurface
  surface.ts     PiSurface 接口 + pi 的真实实现
  loop.ts        循环：拉取 → 分类 → 注入 → 义务 → 遥测（只依赖 PiSurface）
  herdr.ts       Herdr 接口 + herdr CLI 的真实实现
  command.ts     spawn 命令的 shell 切词与引用，以及 pg_spawn 参数到 pi 旗标的映射
  pgclient.ts    平台 HTTP 客户端（只用 ../PiGroups/docs/设计说明.md §10 的 15 个端点）
  org.ts         开组织：发现平台代码、拉起 detached 平台、bootstrap、org.json
  journal.ts     注入前落盘
  state.ts       义务表、遥测表、合并窗口
  version.ts     适配器版本号（唯一来源，与 package.json 由测试对齐）
```

**`loop.ts` 不许 import `@earendil-works/pi-coding-agent`。** 它只认 `PiSurface`。这是全部可测性的来源。

## 2. 两个接口

### 2.1 PiSurface

```ts
export interface PiSurface {
  /**
   * 把一段文本交给 agent（`steer`）。resolve 表示 pi 收下了这条消息（`pi.sendMessage` 返回），
   * **不表示新的 run 已经启动**，也不表示模型看到了：`sendMessage` 是 void，pi 会吞掉启动失败；
   * 忙碌时它插进当前这一轮的下一个模型调用，长工具期间要等工具返回（见 §8.1 与概念稿 §8.2）。
   */
  deliver(text: string, kind: DeliverKind): Promise<void>;
  /**
   * 请求切断正在跑的那一轮，并在 `ABORT_IDLE_TIMEOUT_MS`（3 s）内等它空闲。
   * 没有在跑就立即返回。上限是真实边界：pi 不会强杀一个忽略 abort signal 的工具，
   * 3 s 后放弃并打 warn，abort 请求仍然有效。`signal` 用于 `stop()` 提前结束等待。
   */
  abort(signal?: AbortSignal): Promise<void>;
  /** 当前是否有 turn 在跑。投递**不再**用它当闸门；它只用于 `idle_owed` 与 inspect 的 phase。 */
  isBusy(): boolean;
  /**
   * 这个 session 最后一条助手正文；还没有过就是 `undefined`。由 pi 的 `message_end` 维护，
   * 供 `pg.attention` / `pg.inspect_result` 的 last 块使用（概念稿 §8.5）。
   */
  lastAssistantText(): string | undefined;
  /** 空闲时回调；返回退订函数。 */
  onSettled(cb: () => void): () => void;
  /** 原始事件流：遥测与投递副本的唯一观测通道。返回退订函数。 */
  onEvent(cb: (e: PiEvent) => void): () => void;
  /** 有序退出这个进程。 */
  shutdown(reason: string): void;
}

export type PiEvent =
  | { type: 'turn_start' }
  | { type: 'turn_end'; error?: { message: string }; aborted?: true } // error 存在 = 非正常结束；aborted 是投递层要重投的那一种
  | { type: 'tool_start'; name: string; argsPreview: string }
  | { type: 'tool_end'; name: string; ok: boolean };

export type DeliverKind = 'message' | 'control' | 'nudge' | 'digest' | 'scheduled';
```

**`onEvent` 是必需成员，不是可选的。** 少了它，`stalled` 和 `error` 两个遥测态无法推导（概念稿 §5.1 的第一条失败模式就废了）。宁可让没有事件源的面实现在类型上过不去，也不要造一条"遥测悄悄消失"的降级路径——这是本项目一直在猎杀的那类静默失败。

真实实现的映射（按 `pi-coding-agent@1.4.0` 的实际事件名核对过）：

| pi 事件 | `PiEvent` |
|---|---|
| `agent_start` | `{type:'turn_start'}` |
| `tool_execution_start` | `{type:'tool_start', name, argsPreview}` |
| `tool_execution_end` | `{type:'tool_end', name, ok}` |
| `agent_before_settle` 的 `outcome` | `{type:'turn_end', error?:{message}, aborted?:true}` —— `completed` 无 error，`aborted` / `error` 带；`aborted` 同时置 `aborted:true` |
| `agent_settled` 的 `aborted === true` | `{type:'turn_end', error:{message:'turn ended: aborted'}, aborted:true}` —— 仅当这一轮还没有被 `agent_before_settle` 关过。**被 abort 的一轮不经过 `agent_before_settle`**，实机验证，2026-11-01，见 `probe/`；若 abort 落在别的扩展的异步边界里，`before_settle` 可能先到，这时不能再补一次，否则一轮两个 `turn_end` |
| `message_end` | 只取 `role:'assistant'` 的正文块，存成 `lastAssistantText()`。只有工具调用的消息**不**清除上一条正文："最后一句话"不是"最后一条消息" |

`deliver` → `pi.sendMessage(…, {triggerTurn:true, deliverAs:'steer'})`；`abort` → 会话的 abort 并等 idle；`shutdown` → `ctx.shutdown()`。

**首次实机要验三件事**，验不过就回来改接口，不要改循环：
1. 在 `agent_settled` 回调里调 `deliver` 能真的起一轮（不是被当成"正在 streaming"拒绝）。**已验：通过，包括 `aborted:true` 的 settle。**
2. 一个正在跑 tool call 的 turn，`abort()` 能切断并等到 idle。**已验：只对配合的工具成立。** 工具忽略 abort signal 时 pi 不会强杀它，`isIdle()` 要到工具自己返回才变 true（实测 60 s 工具、58 s 后才 settle）。所以 3 s 上限是真实边界，不是保守值。
3. `shutdown()` 之后进程干净退出，session 落盘。**部分验：SIGTERM/tui 证明处理器被 await、exit 0；`ctx.shutdown()` 自调用、print/json、session 落盘未验。**

### 2.2 Herdr

```ts
export interface Herdr {
  /**
   * 在 workspace 里起一个新 pane 并启动一个 pi。返回 pane 与标签。
   * `args` 是已经切好的额外 pi argv，追加在 `PIGROUPS_SPAWN_CMD` 之后（§2.2）。
   */
  spawn(opts: {
    label: string;
    env: Record<string,string>;
    cwd?: string;
    args?: string[];
  }): Promise<{ pane: string }>;
  /** 等到该 pane 里的 agent 启动完成（idle / done / blocked 任一，见下）。 */
  waitReady(pane: string, timeoutMs: number): Promise<void>;
  /** 读该 pane 的原始文本（只用于诊断与上报）。 */
  read(pane: string, lines: number): Promise<string>;
  /**
   * 关掉 pane。已经不在的 pane 算成功（`pane_not_found` 不是一个要重试的失败）。
   * `forced` 表示等待上限到点时 agent 仍在 `pane list` 里，pane 是在它还活着时被切掉的。
   */
  close(pane: string): Promise<{ forced: boolean }>;
}
```

真实实现 shell 出到 `herdr`。以下命令形状**已对着 `herdr --version` 的实机帮助核对过**（`agent start --help` / `agent wait --help` / `pane split --help`），不是凭记忆写的：

| 动作 | 命令 |
|---|---|
| 起成员 | `herdr tab create --no-focus --label <名字> --workspace <我的 workspace> [--cwd <path>] --env K=V …`（新 tab，不是分栏；**必须显式给 `--workspace`**，不给时 herdr 用的是**焦点所在**的 workspace，成员会被撒到别的工作区去） |
| 启动 agent | `herdr agent start <label> --kind pi --pane <id> --timeout <ms> [-- <extra args>]` |
| 等就绪 | `herdr agent wait <pane> --until idle --until done --until blocked --timeout <ms>` |
| 读终端 | `herdr agent read <pane> --lines <n>` |
| 关 pane | `herdr pane close <pane>`（先有界等待：每 200 ms 读 `pane list`，等该 pane 的 agent 消失，最多 5 s；`pane list` 读失败不等，直接关。到点 agent 还在时报 `forced: true`） |
| 退化路径 | `herdr pane send-text <pane> "<PIGROUPS_TOKEN=… pi>"` |

四条已核实的细节，写在这里免得下次又猜：

1. **环境变量走 `tab create --env KEY=VALUE`**（"Set an environment variable for the launched process"）。`agent start` 没有 `--env`。所以父传 token 给子的机制是：先起 pane 并把 env 塞进 pane 的启动环境，再在那个 pane 里 `agent start`。
2. **等待的旗标是 `--until`，不是 `--state`**。可取值 `idle | working | blocked | done | unknown`；`--until` 可以重复，不给时 herdr 自己匹配 `idle / done / blocked`（`herdr agent wait --help` 原文）。不给 `--timeout` 会无限等——所以适配器必须自己带上限。
3. **`agent start` 要求目标 pane 处在一个交互式 shell 提示符上**。所以顺序是"先起 pane（shell）→ 再 start"，不能反过来。

**成员就绪的判据不在 herdr 里。** `waitReady` 只回答「herdr 认出了那个 pane 里有个 agent」（`idle`/`done`/`blocked`/`working` 任一，除 `unknown` 之外）；**真正决定「成员就绪」的是平台**：`GET /v1/members/{id}` 的 `last_seen_at` 非空，说明子成员的适配器已经连上平台（URL 对、token 对、轮询活着）。用 herdr 的界面状态当就绪判据已经错过两次：`done` 不是 `idle`，而一个拿到长简报的子成员会立刻进入 `working`。herdr 只在超时时用来分辨「进程没起来」还是「起来了但连不上平台」。
4. **就绪不等某一个标签**。`waitReady()` 重复三次 `--until`：`idle`、`done`、`blocked`，与 herdr 不给 `--until` 时的默认匹配集合一致。原因是 brief 在 pane 起来之前就投了，子成员常常已经开始（甚至跑完）第一轮；herdr 把跑完一轮记成 `done`，只看 `idle` 会把它误报成起不来，走满 `SPAWN_READY_MS` 后抛 `timed out waiting for agent status`，调用方还可能因此重试出重复成员（真机证据 `probe/logs/spawn-args-20261101T142926/ready-probe/`）。`blocked` 也是活着的 agent（在等输入或许可），不是启动失败；把它排除会把同一种误报换个标签重演。`working` 仍不匹配：它是已经启动、正在干活，等它安静下来不是 spawn 的判据。超时与错误文本保持不变：pane 真的没起来时仍以原来的 `timed out waiting for agent status` 失败。

**spawn 命令的结构与优先级（0.4.0 起）。** 子成员是一个**正常的 pi session**，不是一次性的 subagent，也不是被剥干净的 worker：它应当像一个持久的队友，按正常 pi 启动继承操作者的工具、技能、prompt template、MCP server 与 `AGENTS.md` 等上下文文件。默认只把本适配器加进这个环境，不拿掉任何东西。`src/extension.ts` 用 `import.meta.url` 取自己被加载的绝对路径，默认命令是：

```
pi -e '<本扩展的绝对路径>'
```

以前忘了给 `PIGROUPS_SPAWN_CMD` 加 `-e .../src/extension.ts`，`pg_spawn` 仍会建成员、开 pane，但子 pi 没加载适配器：不轮询、不收简报、也没有 `pg_*` 工具——表面成功，实际不是成员。现在父适配器知道自己的路径，这个坑由默认值填掉。**不加 `-ne`**：不剥离扩展是刻意的产品选择，成员要像人手动起的 pi 一样工作。

`PIGROUPS_SPAWN_CMD` 覆盖的是**整条基础命令**（操作者级逃生口）。`pg_spawn` 不镜像 pi 的启动参数：它只接受一段原始 `args: string[]`，按调用方给的顺序追加在基础命令之后，一个元素一个 argv。凑成什么命令行只有两步：

1. 配置的基础命令：`PIGROUPS_SPAWN_CMD`，缺省为上面的 `pi -e '<本扩展绝对路径>'`；
2. `args` 的每一项，按顺序原样追加。

这里**没有**适配器维护的旗标映射表。早期版本曾镜像 `model` / `thinking` / `tools` / `exclude_tools` / `extensions` / `skills` / `prompt_templates`，现已删除，原因有两条：一是多一层翻译没有增加信息，`args` 已经能表达同样的事；二是 pi 的旗标远多于任何一张我们会维护的表，每加一个旗标都要适配器发一次版。模型不知道某个旗标时应当自己跑 `pi --help`——那是 pi 自己的手册，不是本适配器的 schema。

**`args` 不做消毒。** 调用方可以传 `-p`、`--` 或任何改变子进程启动方式的旗标，这是调用方的选择，适配器不拦也不改写。唯一的保证是每个元素保持为一个 argv：不合并、不拆分、不重排，相同参数集产生相同 argv（没有随机量）。工具 schema 用 `additionalProperties: false` 拒绝未知参数名。

命令按 shell 引号规则切词（单引号、双引号、反斜杠），所以扩展路径含空格时仍然是一个参数；`pane send-text` 兜底路径把同一条命令交给 shell，也按同一规则解释，并且对每个追加的 argv 元素用同一个 `shellQuote`，路径里的空格、`$`、引号、分号不会越出一个参数。父适配器把生效的 `PIGROUPS_SPAWN_CMD`（默认值或显式值）传给子成员的环境；`pg_spawn` 的 `args` 只作用于这一次 spawn，不会写进子成员继承的基础命令，所以孙子成员沿用同一条基础命令。

`org.ts` 不依赖 pi：它只碰进程、文件、HTTP。`loop.ts` 仍然只依赖 `PiSurface`。

四条约定（0.5.0 起；旧版的"一次 settle 只投一次"和 `isBusy()` 闸门随 steer 一起删掉了，见概念稿 §8.1）：

1. **时间只有一个来源。** 所有"过了多久"都用注入的 `now()` 算；`tick()` 的调度用真实 `setInterval`（5 秒），但**判定**只读 `now()`。测试推进假时钟后直接调 `tick()`，不睡。
2. **`start()` 只是把轮询与定时器挂起来**，逻辑都在 `pollOnce` / `flush` / `tick` 里。所以测试可以完全不用 `start()`。

   这一条有个必须遵守的推论：**对 `onSettled` 的订阅发生在构造函数里，不能只在 `start()` 里。** 反应负责名册复核、pane 复核、跑一次 `tick()`、以及把催办标记成"该催了"。把订阅绑在 `start()` 上，等于"不启定时器就收不到空闲事件"，而 §4.1 的剪除和 §4.3 的催办都挂在这条反应上。

   **settle 不是投递触发器。** 投递只有一条路：**翻滚时间窗**（概念稿 §8.1）。

   - 队列里第一个 `windowed` 项到达时开窗；`tick()` 发现 `now - windowStart >= deliveryWindowMs` 时把整批**一次**投出去。没有第二个定时器。
   - 投递不等空闲：`deliver` 是 pi 的 `steer`。忙时它插进当前这一轮的下一个模型调用；长工具期间要等工具返回（`probe/logs/steer-20261101T170244Z/`）。
   - **例外只有三个，都是 `windowless` / 立即到期，不是第二条投递通道**：启动简报不带窗口（§8）；abort 之后立刻关窗投递（概念稿 §8.3 ①），且把下一批也标成"立即投"，否则"先 abort 再 say"里那条 say 要白等一个窗口；`poll` 401 那句"token 失效"在 `stop()` 之前投送（§9）——循环一旦停下就拒投，它只能抢在停下之前走。三个例外都还是同一条队列、同一次 `deliver`。
   - **条数上限只是尺寸阀门，永远不是触发器。** 一个窗口最多投 10 条；剩下的留在队列里，等**下一个窗口**（重新开窗），不会因为"又攒了 10 条"立刻再投。
   - **催办只在没有别的东西可投的窗口里投**（§4.3）。settle 只是把 `nudgeDue` 标上；队列里还有真实消息时，那批消息就是唤醒，催办等一个安静窗口。
   - **`flush()` 可重入安全。** 定时器、工具、测试可能同时调；并发调用合并成同一次投递，`pending` 取出的一批不能被另一个 `flush` 重复拼接，闲聊计数也不能追加两次。

   **"在飞的活"包括表面还握着的投递。** `surface.deliver` 已经交出但还没返回的那一批，也是在做的事；`stop()` 提前返回就等于"报告安静了，其实模型正在被递东西"。批量投递和催办两条路都必须登记，`stop()` 一起等。

   **也包括还没走到投递的 settle 反应。** 反应在投递之前要先 await 平台（名册、pane 复核）；这段窗口里 `deliveries` 还是空的，只看投递集合的 `stop()` 会提前返回。所以 `stop()` 同时等待所有在飞的 settle 反应，反应在每个 await 之后重查 `stopped`，停下来之后一笔都不投。`stop()` 之后连手动 `flush()` 也不投（`deliverPending` 直接答 `stopped`）。

   **但是有上限**：等不到就放弃，不是错误——被卡住的是表面的问题，不是关停的问题。默认 3 秒。没有上限的话，一个永远不返回的 `deliver` 会把整个进程的退出挂死，而退出是删成员路径上的最后一步。
3. **发出消息只能走 `say()`**。它同时维护“欠回复”账本——工具层不许绕过它直接 `POST /v1/messages`，否则这条会话的 flag 永远不会被清。`pg_ack` 是另一个入口，它也清 flag，但不发消息（§4.3）。
4. **投递成功不是投递生效。** `surface.deliver` 返回只代表 pi 收下了。所以投递层留一份**内存副本**——一张**未确认批次表**（列表，不是槽位）：`turn_end` 带 `aborted: true` 时把全部副本平铺回队首并立刻重投（绕过水位——水位在交付时已经推进了）；**干净结束**和**provider error** 都丢掉整张表；只有 abort 那条路保留重投。列表有上限（`UNACKNOWLEDGED_BATCH_LIMIT = 8`）。完整规则与实测依据见 §3.4；0.5.0 的单槽位做法已在 0.5.1 废掉。

`src/extension.ts` 只做翻译：`pi.registerTool` → 这些方法，`pi` 事件 → `PiEvent`。

## 3. 循环

两个独立的异步任务，加上 settle 反应：

```
pollLoop     每轮 GET /poll?wait=25&limit=20 —— 不依赖 isBusy
timerLoop    每 5 秒：预约到期、义务复查、遥测窗口到期、投递窗口到期
settle反应   tick()（同步判定）+ 名册/pane 复核 + 标记催办；不直接投递
```

### 3.1 一轮拉取的处置

```
batch = poll()
journal.append(batch)            // ① 先落盘，再谈注入

for item of batch.items:
  control  → 立即处置（见 3.2）
  message  → 分类（见 3.3）→ 入队（第一个 windowed 项开窗）

flush()                          // 窗口到期才真的投；否则什么也不做
journal.commit()                 // 整条 entry 的每一项都交付后才清
```

`journal.commit()` 之前崩溃 → 重启后重放整批。重放可能重复注入，所以注入文本必须带消息号。
重放项和普通消息一样走投递窗口（概念稿 §8.1 的例外只有启动简报、abort 后的强制关窗、以及 §9 的 401 提示）。

### 3.2 控制项

| `cmd` | 处置 |
|---|---|
| `sys.terminated` | 先按 `pg.abort` 同一条有界规则切断正在跑的那一轮（`ABORT_IDLE_TIMEOUT_MS`，不注入提示），再丢弃 journal 里未注入的（已经 gone，写了也 410），停循环，最后 `shutdown()`。abort 期间不投递，settle 也不能在中间起一轮 |
| `pg.abort` | `abort()`；**不注入任何提示**。切断完成后**立刻关窗投递**已排队的东西，并把下一批也标成"立即投"（概念稿 §8.3 ①） |
| `pg.steer` | 把 `payload.text` 作为 `control` 类注入，**走投递窗口**。工具面上已经没有 `pg_steer`；这条是线协议兼容。"改方向"用 `pg_say`，只有 `pg_abort` 能在长工具期间改变行为（概念稿 §8.2） |
| `pg.inspect` | 立刻回 `pg.inspect_result`（读当前 phase / 工具 / 义务） |
| `pg.attention` | 只更新上级的遥测表，**本身不注入**；`gone` 例外：立即让合并窗口到期（元 §5.2） |
| `pg.inspect_result` | 只交给在等它的 `pg_inspect`（超时就当没答） |
| 其它未知 `cmd` | 原样注入，标 `kind:'control'`（平台不知道内容，适配器也不该丢） |

**控制项串行处理**，按 `control_seq` 顺序逐条 await。`pg.abort` 之后再来的 `pg.steer` 必须等 abort 完成；abort 结束时的关窗投递把同一批里排在它后面的 steer 一起送出去。

### 3.3 消息分级

只有三档，没有分类器：

| 条件 | 处置 |
|---|---|
| 控制字 | 见 3.2 |
| `mentions_me` 或 `from_parent` 或会话是 `dm:` 或群里的 `@all` | **注入**，并置该会话的欠回复 flag（`@all` 整个会话只置一条） |
| `gap` 且 `mentioned > 0` | **注入一行**（带锚点），并置该会话的欠回复 |
| `gap` 且 `mentioned == 0` | 不注入，只把 `count` 计入闲聊计数 |
| 其余 | **不注入**，只计数 |

被计数的条数在下一次有注入时附在末尾（`[and 3 unrelated messages]`），否则静默丢弃。**不为闲聊起一轮。**
（尾部这一行与下面的 gap 行都是**注入进模型上下文的文本**，所以是英文；与 P7 一致。）

**`gap` 为什么要分两种。** 平台在成员积压超过 `limit` 时把更旧的消息折叠成一个 `gap`，里面带 `to` / `count` / `before` / `mentioned`。`mentioned == 0` 说明漏掉的都是无关闲聊，把它计进闲聊即可，不值得起一轮；`mentioned > 0` 说明**有直接点名的消息被跳过了**——那正是最不能静默丢的情况，所以给它一行带锚点的提示，并把它算作一次点名：

```
[<to> skipped 12 messages, 2 of them mention you; backfill with pg_read(to, before=<before>, limit=20)]
```

两种都要进 journal，重启后一起重放。

注入一条消息时用的文本：

```
[<to>#<seq>] <from_name>: <preview>
```

若 `preview` 被截断（≤200 字符），模型需要全文时自己用 `pg_read`。

### 3.4 注入去重：每会话一个水位

**`journal` 也必须按成员分，理由和水位一样。** `spawnMember` 会把 `PIGROUPS_ADAPTER_DIR` 传给子成员，所以父与子共用一个目录，而 `dm:<a>_<b>` 这个会话 id 在两端是同一个字符串。一个目录一份 journal 会有三个后果：子成员重启时重放**父的**批次，把父的消息注入进自己的上下文；重放后的 commit 把**父的**那份删掉，父再崩就没得补；子成员收到 `sys.terminated` 时 `discard()` 把父和兄弟的批次一起清掉。所以路径是 `<adapterDir>/journal/<memberId>/`。

**同一条消息只能注入一次，不论它从哪条路来。** 三条路会撞车：

| 来源 | 什么时候 |
|---|---|
| 启动简报（§8 第 3 步） | 启动时读父 DM 的最后一条 |
| `poll` 投递 | 那条消息同时也还在平台的 inbox 里，因为成员从没 poll 过 |
| journal 重放 | 进程崩在"取走之后、注入之前"，重启重放 |

三者都可能指向同一个 `(conv, seq)`。所以适配器为每个会话维护一个**注入水位** `injected[conv] = 最大已注入 seq`，**持久化在 `PIGROUPS_ADAPTER_DIR`**：

```
要注入 (conv, seq) 时：
  if seq <= injected[conv]: 丢弃（已注入过）
  else: 注入；injected[conv] = seq；水位落盘
```

一条规则同时覆盖三种来源。持久化是必须的——否则"启动简报已注入、但 inbox 里那份还没取走"这种重启会重复，而这个窗口正是崩溃后最常见的位置。

**`gap` 项不推进水位。** 平台 §6.4 说 `gap.before` 是"回补锚点"，而当那个会话一条都没保留时它等于"最近一条被跳过消息的 seq + 1"——**下一条真实消息的 seq 正好等于它**。拿 `before` 去推进水位，那条消息就会被当成"已注入"直接丢掉，而 gap 是一次性信号，再也不会重来。水位的语义是"已经给模型看过的最大 seq"，回补锚点不是看过的东西。

这条水位和平台内部的消息游标是**两套东西**：平台的游标记的是"投递到哪"，这里记的是"注入到哪"。平台是取走即消费，所以它那份指针无法替你回答"这条我是不是已经给模型看过了"。

**确认边界（必须说清，别当成"已送达"）**：水位与 journal 在 `deliver()` resolve 之后推进，而 `deliver()` 只等到 `pi.sendMessage` 返回——pi 1.4.0 的 `sendMessage` 是 void，启动 run 的异步失败会被 pi 吞掉（`agent-session.js` 的 `sendCustomMessage` 不被 await）。所以存在一个丢失窗口：**消息已被标成已注入、journal 已提交，但那一轮其实没起来**。适配器无法从 `PiSurface` 观察这个失败；`handoff.md §7` 记着这条窗口。

**2026-11-03 的决定是：不收紧它，投出去就算看见。** 这条路是通的——pi 的 `before_agent_start` 带
`messageType:"custom"` 和起始 `message`，可以当确认用——但它只覆盖“空闲被叫醒”那一种投递，
不覆盖“忙时 steer 进正在跑的回合”；为剩下那一半再养一套确认状态，代价大于它省下的东西
（实测重复总量只占 cacheRead 的 0.24%，而“保留整个回合”那种保守做法反而制造了 29 次陈旧重投）。
**用“极小的丢失概率”换“零确认状态”，比反过来划算。**

**实测到的第二种丢失（2026-11-01，`probe/logs/steer-20261101T170244Z/`；同日复验 `probe/logs/v3-20261101T173805Z/`）**：一条已经交给 pi、但还排在一个长工具后面的 steer，如果这时 abort 落地，它会**整份 session 文件里一次都不出现**。所以投递层留一份内存副本——一张**未确认批次表**（`unacknowledged: PendingDelivery[][]`），按投递顺序排列：

- 每次成功 `deliver` 后**追加**这一批（不是覆盖一个槽位）：同一轮可以跨两个窗口各投一批，abort 会把两批都拿走；
- `turn_end` 带 `aborted: true`（D3 的 abort 分支）→ 把**所有**未确认批次按投递顺序平铺回队首、窗口标成立即到期，绕过水位（水位已推进，`enqueue` 的去重会把它们丢掉）、重新投递；
- `turn_end` **干净结束** → 丢掉整张表（pi 已经把它们都落盘了）；
- `turn_end` 带 provider **error** → **也丢掉整张表。** 判据是“投出去就当模型看见”：`sendMessage` 是 void，
  出错时从接口上无法区分“落盘了”和“没落盘”；而保留整张表会把 **一个回合里投递过的所有东西**
  都变成可疑。2026-11-03 的真实运行（quant 组织，19 个会话 / 775 条注入）里抓到了这个代价：
  31 个 `(会话,序号)` 被投递两次，**29 个的两次间隔 ≥120 秒，中位 650 秒，最长 1839 秒**。它们的机制查实了：
  **31 个全部集中在 5 个会话里，而这 5 个会话各收到过恰好一次 `pg.abort`，时间就在第二次投递那一刻**
  （平台 `controls` 表的 6 条 `pg.abort` 对得上）。abort 会丢掉所有未确认批次、重新投递，
  而“保留整张表”让这些批次从投递那一刻起直到半小时后的 abort 都处于“可疑”状态——
  包括模型已经照着它干完活的那些。

  查这条时踩过一个坑，记下来：**abort 切断在飞请求时，session 文件里记的 `stopReason` 是 `error` 而不是 `aborted`**，
  所以“两次副本之间没有 aborted 回合”推不出“没发生 abort”；证据要在 `controls` 表里找。

  代价换算：重复投递占全部投递的 3.1%（31/997），按 token 只占 cacheRead 的 0.24%。
  **用这点重复去换一个几乎测不到的丢失窗口不划算**：宁可承认“投出去就算看见”，
  也不要在一次普通的 provider 报错之后，把半小时前的消息重播一遍。
- 表有上限（`UNACKNOWLEDGED_BATCH_LIMIT = 8`：默认窗口下一轮跨八个窗口，最多 80 条）。超了丢**最旧**的一批并 `console.warn`——这是丢了副本，不做静默裁剪；
- 副本只在内存里。崩溃丢副本 = 可能少一次重投；重复注入由 `[会话#序号]` 兜住。

0.5.0 的这个位置只有一个槽位（`lastDelivered`），同一轮里第二个窗口的投递会覆盖第一个；那一版把它记成已知缺口（`probe/logs/v3-20261101T173805Z/extra-multibatch-loss.ts`：`#2` 出现两次，`#1` 一次都没有）。0.5.1 换成上表，`test/delivery.test.ts` 的 “two batches steered into one still-running turn…” 在旧槽位上变红、在表上变绿。

### 3.5 注入的合并

一个投递窗口一次 `deliver`，最多 10 条，按到达顺序。**条数不是触发器**：超过 10 条时剩下的留在队列里，适配器重新开一个窗口，下一个 `tick()` 到期时才投。空闲与忙碌都不改变这条规则——投递是 steer，不等空闲。

## 4. 欠回复

### 4.1 判定

某个会话欠回复 ⟺ **该会话有一个未清掉的 flag**。flag 只能被下面四类消息置起来（它们在 §3.3 里正是“置欠回复”的那几行）：

- 它 `mentions` 包含我（群里的 `@all` 也算，但只给整个会话置**一条**，一次答复/确认就清掉）；
- 发送者是我的父；
- **这个会话是一对一**（`dm:`）——一对一里的每一条都是发给对方的，不存在"没点名"这回事；
- `gap` 且 `mentioned > 0`（§3.3 的第三行）——漏掉的里面有点到我的名，同样置 flag。

第三条是必须的：少了它，兄弟之间的一对一会退化成“说了但没人欠回复”，而那正是沉默的 idle 最常见的样子。§3.3 的分级表里写了 `dm:` 要置欠回复，这里必须一致——同一件事不能有两套判定。

**为什么债是一个 flag，而不是“从历史推导出来的一条关系”。** 早先的判定是“该会话最后一条消息不是我发的”。
它有两个后果，都在 2026-11-03 那场真实运行里量化过（19 个会话、4,809 次请求）：

1. **不清不掉的债只能靠说话来清。** 历史里只有消息，所以唯一的清除方式是“我发出一条消息”。
   于是两个想收尾的成员会互相把对方的债重新置起来：实测 **17 次 ack↔ack 往返**，
   最后撞上 3 次催办上限，变成 **14 次** `no output after 3 nudges` 的 blocked 上报。
   设计当初给的出口是「回复，或说明为什么不需要回」——**那句“说明”本身也是一条消息，又给对端置一次债**，
   而那份说明没有任何人或 agent 会去读：出口后面没有人。
2. **一个来源一次答复就够了。** 历史推导只能回答“最后一条是谁发的”；flag 能回答
   “我看到过到某个序号为止的全部消息，并且已经处理完了”。

所以：**flag 由投递置起来，由“回复”或“确认”清掉**（§4.3 的 `pg_ack`）。
一个 flag 覆盖它之前到达的全部消息——回复前来了五条，仍然只欠**一次**回复或**一次**确认。

**前置条件：一对一会话的对端必须还活着。** 对方被删掉之后，这条债在物理上无法偿还——每次发送都会得到 `member_gone`——而平台不会替谁撤销这个标记。所以 `dm:` 那一条要加一个条件：`dm:` 的另一方仍在 `GET /v1/tree` 的名册里。名册按 30 秒缓存（`ROSTER_TTL_MS`），只在有 `dm:` 债时读，读失败就**不剪**（错剪会丢一条真债，晚剪什么也不丢）。

名册是**快照**，所以还要防它另一个方向的错：对端可能是在这次快照**之后**才被创建的，快照里没有它不等于它死了。剪除只判**比快照更老**的债：

```
债.since < 快照.at   → 这个快照能对它的对端下结论
债.since >= 快照.at  → 对端可能是在快照之后才出现的，不剪
```

`since` 是这条会话的 flag **从空变非空的那一刻**（§4.2：flag 已经置着时不重写）。没有这条，一次 30 秒 TTL 内的新建同级成员会把它刚发来的消息判成"对端已死"，真债直接消失。

**读到的 200 不一定就是名册。** `{"nodes":[]}`、`{"ok":true}`、`[{}]`、非字符串 id 都是真出现过的形状；前一种能一次清空所有私聊债。所以名册必须同时满足：`nodes` 是数组、每个节点有非空字符串 `id`、并且**包含自己**。任何一条不满足，就把这次读当成失败——不剪任何债。读失败时也丢弃缓存，下一次 settle 重新读。

三个已知的死亡时刻各自有更快的路径：`terminate()` 成功后立刻剪掉平台级联返回的**每个**成员（不只是参数——孙子成员的债也会留下）的私聊、发送收到 410 时立刻剪掉、其余靠名册复核。

这就是全部定义。**它不是从历史推导出来的**：flag 是本地状态，必须落盘（§4.2），
否则重启会把已经确认过的会话全部重新标成欠回复——“不需要任何本地状态”这条性质，代价就是“无法确认”。

### 4.2 维护

欠回复 flag 是**本地状态**，落盘在 `PIGROUPS_ADAPTER_DIR/owed/<memberId>.json`，和注入水位同一套目录：

```json
{ "owed": { "dm:m_a_m_b": { "seq": 71, "since": 1793689123456 }, "g:g_1": { "seq": 12, "since": 1793690000000 } },
  "acks": [ { "conv": "dm:m_a_m_b", "seq": 71, "at": 1793689200000 } ] }
```

`seq` 用来在 §4.3 的文本里点名；`since` 只在 flag 从空变非空时写一次，留给 §4.1 的名册快照做判断。

- **投递时置**：一条消息被投入上下文，`owed[conv] = seq`。seq 只用来在 §4.3 的文本里点名，
  不改变“一次答复”的语义。
- **回复时清**：`say(conv)` 成功后 `owed[conv] = null`。
- **确认时清**：`pg_ack(conv, seq?)` 成功后 `owed[conv] = null`，并记一条 `acks`。
  确认与回复**在清 flag 这一件事上等价**，但确认**不清**催办计数、**不结束**阻塞回合——
  “不开口”本身就是需要被看到的事，所以它另有自己的上报（§4.3 的 `silent acking`）。
- **启动简报不置 flag**：`pg_spawn` 发给新成员的那份任务书是一对一，按上面的规则会给它自己置一条债，
  而它没法“回复”自己的任务书。简报的 `(conv, seq)` 已知（`spawnMember` 就是发它的人），跳过它。
- **重启时 load**：flag 是状态，不是推导出来的事实。文件缺失（首次启动、或从旧版本升级）时
  才做一次全量对账（见下），文件存在就以文件为准。
- **兜底对账**：`GET /v1/conversations` 的每个会话做一次 `GET /v1/messages?to=<conv>&limit=1`，
  按 §4.1 的四条判据**加上“读到的那条不是我发的”**决定要不要置 flag。只在没有 flag 文件时跑。
- 每次 `agent_settled` 后若表非空且队列为空，把 `nudgeDue` 标上，由下一个到期窗口投递（§4.3）。

### 4.3 催

```
if owed is empty: return
把**所有** owed 会话合成一条文本，只 deliver 一次（英文：注入的是 prompt，不是给人读的报告）：
  Unanswered messages: <conv> #<seq>, <conv> #<seq>. Reply, or call pg_ack to clear this notification.
```

**必须是合并后的一次投递**，不是每个会话各投一次：催办的目的本来就是"让模型醒一次去看"，醒一次就该看到全部欠账。它走投递窗口，而且**只在队列里没有别的东西可投时才投**（`nudgeDue` + 空队列）。settle 只负责标记，投递由 `tick()` 在窗口到期时做——settle 不是投递触发器（§2.3）。

**文案为什么是“回复，或者调用 `pg_ack` 清掉这条通知”，而不是原来的“回复，或说明为什么不需要回”。**
“说明”是一个**没有出口的出口**：它是一条消息，会给对端置一次新债（§4.1），而没有人读那份说明。
`pg_ack` 把“我不打算回”变成一次**本地动作**——清 flag、不发消息、不产生新债。
这也是唯一能让双方体面收尾的方式：一端 ack 之后，对端的最后一个未读消息被消化掉，链条就断了。

`pg_ack` 的形态与护栏：

```
pg_ack({ conv: string, seq?: number, all?: boolean })
→ { cleared: [{conv, seq}], remaining: [{conv, seq}] }
```

- `conv` **必填**。要清掉全部会话必须显式写 `all: true`——一次静默抹掉所有债，等于把“有没有活没干”
  这件事从记录里删掉，不能让它成为默认行为。
- `seq` 只能 ≤ **本适配器为该会话点名过、投递过、或 `pg_read` 读到过的最大序号**。不能用注入水位当上限：
  `gap` 的 `seq` 是回补锚点，它置了 flag 却**不推进注入水位**（§3.4），用错上限会让模型
  照催办文本去 ack 时被自己拒绝。模型也不能确认一条它没见过的消息——而 `pg_read` 正是让一个更晚的
  seq 变成可确认的那条路（它抬的也是这个上限）。
- `all: true` 时 `seq` 与 `conv` 都被忽略（那一次调用就是“把账本清空”）。
- 没有欠账时 `pg_ack` 是**静默的 no-op**（`{cleared: [], remaining: []}`）：上限是“不许确认没见过的消息”的护栏，
  不是“必须存在欠账”的前提。
- 确认是**静默**的：不发消息、不进任何人的上下文。但它必须能被审计，所以记在本地 `acks`；
  同一会话连续 ack ≥3 次且期间没有任何回复时，进入 `silent_acking` 状态（§5.1）——它比确认多一层含义：
  “这个成员的答复都是零内容的”，而那正是父级需要知道的事。

**群聊里的 `pg_ack` 与 DM 完全同义，而且必须保持静默。** 触发条件没有变（§4.1 那四类：
`dm:` 里的每一条、群里 `mentions` 到我、群里的 `@all`、`gap` 且点名；`@all` 只产生一条）。
`pg_ack` 只清掉本地那个 flag，不广播、不产生消息。

**为什么不能做“可见的确认”。** 一条不带 @ 的群消息，按 §3.3 只会被计入闲聊计数、**根本不会被投递**
（`gap` 且 `mentioned == 0` 也不注入）。所以一句“我看到了”谁都收不到，却要占掉每个成员一次 poll；
要让它被看见就得 @ 人，而 @ 又会给对方置一条新债——又回到 §4.1 那个循环。
所以让“静默确认”留下痕迹只能靠两条：本地 `acks` 审计记录，以及连续 3 次的 `silent acking` 上报。

**上限**：同一会话连续催 3 次且期间它没有发出任何消息 → 停止催，并进入 `blocked` 状态（§5.1）上报给父；
一旦这个成员真的发出消息，状态就回到 `recovered`。这条上报不需要模型参与。

**同一段催办文本不重投，但跳过也算一次。** 本会话上一次投出的催办文本与这一次逐字相同时**不投递**，只记一行日志。
实测 62 次逐字重复注入里 61 次是催办，跳过它不损失信息——同一条 `(conv, #seq)` 已经在上文里。

**跳过的这一次仍然要计进催办预算。** 理由与“不消耗”相反且更强：一条冻结的债（对方已死、文本不再变化）
永远产出同一段文字，不计预算的话 `no output after 3 nudges` **永远不会发出**——而 `idle_owed` 又不进汇总（§5.2），
父级就同时失去两条信号。计预算之后：模型只被同一段文字打扰一次，父级仍在第三次之后收到一条
“催了三次仍无产出”的结论。前者省上下文，后者保信号，两件事都要。

**为什么这里允许催 3 次，而 §5.2 的遥测只提醒一次。** 两个收件人不一样：遥测的收件人是父级，
它可以随时用 `pg_children()` 自己查；催办的收件人是被催的那个人，**它没有别的渠道知道“有人在等我”**——
推送是唯一的信息源。所以一个一次性、一个三次；三次是硬上限，不会变成 §5.1 那场 6.5 小时的重播。

**这个"阻塞回合"的边界要说清**：从第一次催开始，到**成员自己发出一条消息**为止（`pg_ack` 不算结束，见上）。期间：

- 新到的入站消息**不重置**催办预算，也**不重新触发** blocked 上报——否则父每隔一会儿问一句，就会收到一串重复的 `blocked`。
- 只有 `say()` 成功才算这个回合结束（它清义务表、清计数、清上报去重标记）。
  **`pg_ack` 不算**：它清 flag，但不清催办计数、不结束这个回合（§4.2）；不开口本身就是需要被看到的事。
  下一次再阻塞，就是一个新回合，可以再上报一次。

换句话说：**"已经报过 blocked" 是一个只在成员开口时才失效的状态**，不是"来一条新消息就重置"。

`@all` 只产生**一条**义务（一次回复就清掉整个会话），不是每条一个。

## 5. 遥测

### 5.1 下级侧：边沿触发

监视六个状态，**只在进入或离开时报一次**。父级按住的是**每个子一张活动状态表**，不是"一行一个状态"：
这六个状态里有一半是**按会话**的事实，单槽装不下它们（一个子可以同时在两个会话上 `blocked`，也可以一边 `error` 一边 `blocked`）。

| 状态 | 进入条件 | 字段 |
|---|---|---|
| `stalled` | 同一 tool call 持续 > `PG_ATTENTION_TOOL_MS`（默认 300000） | `tool:{name, elapsed_ms, preview}` |
| `slow_turn` | 一轮持续 > 2× 同一阈值 | `busy_ms` |
| `error` | 一轮以 provider 错误结束 | `note` |
| `idle_owed` | idle 且欠回复超过 `PG_ATTENTION_TOOL_MS` | `owed:[conv…]` |
| `blocked` | 同一会话连催 3 次仍无产出（§4.3） | `owed:[conv…]`, `note` |
| `silent_acking` | 同一会话连续 ack ≥3 次且期间一次 `pg_say` 也没有 | `owed:[conv…]` |

后两个不是运行态，是**账本态**：它们由适配器替成员算出来，进入条件在 §4.3，离开条件是同一个——“成员真的开口了”。
它们能当状态用，是因为它们**确实有生命周期**：催满三轮进去，一句 `pg_say` 出来。早先把它们当一次性通知发（`pg.report`），
结果是“发出去了但没有终态位”，父级只能靠一次注入记住。

恢复时发 `state:'recovered'`，带 **`of:` 原状态名**。属于会话的状态（`idle_owed` / `blocked` / `silent_acking`）的值是**一个会话集合**：
它每次变化（变大或变小）都重发一条同名状态，父级用收到的集合**整体替换**（upsert，不是并集）；**集合变空才发 `recovered`**。
`gone` 是终态，不在 `of:` 的取值里。

**`error` 的离开条件写清，因为它是六个里唯一不能自清的**：下一次**干净结束**的回合（`turn_end` 无 error）就发 `recovered{of:'error'}`；
如果子就死在这一状态里，永远等不到那个回合——所以它必须配一条活性复核（下文第三条路径）。

**表的键是状态名，不是 `(状态, 会话)`。** 一个状态只带一个 `since`（什么时候进入的，集合变化不重置），
所以“还是同一件事”能从 `since` 看出来；“哪个会话”是值的一部分，不另开一行。
选这个形状的理由：一个名字只能对应一个开始时间，否则“这个状态持续了多久”就不存在了。

**为什么必须是“每个子一张表”而不是“一个子一个状态”。** 早先的模型是 `childId → {state, since}`，它假设“一个子同时只处于一个状态”。
这个假设在 `idle_owed` 上已经勉强：一个子可以同时欠两个会话；加上 `blocked` / `silent_acking` 之后直接碎了——
两个会话都被催死时只能记一个，而“A 会话还清了、B 还欠着”没有任何方式表达（发 `recovered` 就是说“全好了”）。
改成活动状态表之后，每个状态自己的进入/离开条件都能如实表达，也不再需要“谁盖谁”的优先级。

**集合变化都要重报，变小也是。** 进入一个已在表里的状态、但带的集合不同（例如 `blocked` 的 `owed` 从 1 个会话变成 2 个，
或从 2 个变成 1 个），都算一次新信息：重发一条同名状态，父级用它**替换**旧集合。
写成“变大重报、变小不报”会让“A 会话还清了、B 还欠着”变成父级永远看到 `[A,B]`——`pg_children()` 返回假事实。
集合空才是 `recovered`。

上报走控制通道 `pg.attention` 给父。**只发给直接父**，没有父（root）就不发。

**“子已消失”必须有三条到达路径，少一条就会出事。** 2026-11-03 那场运行里，三个会话在下级死亡之后
被每 30 分钟提醒一次、连续 6.5 小时（三个会话合计 **42 次投递，其中 39 次是同一份冻结快照的重播**），
根因就是“消失”只有一个来源——`terminate()`：

1. 本进程 `pg_terminate` → 平台级联返回的每个成员都置 `gone`；
2. 子进程优雅退出时发 `pg.attention{state:'gone'}` → 父级把它写进遥测表（§5.1 第二条路径），
   而不是当成一行普通控制文本；
3. 父级必须**独立地**复核每个还在遥测表里的下级：30 秒一次 `GET /v1/members/{id}`。
   这条复核**不能挂在 pane 映射上**：`panes` 只在本进程 spawn 过成员时才填，父级重启后是空的，
   靠它就会一次都不查（现在的 `reconcilePanes()` 正是 `if (this.panes.size === 0) return` 早退的）。
   读到 `status:'gone'` 时既要关 pane，也要喂遥测表。

三条都不在时，`error` 就永远没有“离开”事件——而它恰好是六个状态里唯一**不能自清**的那一个：
其余都靠子成员的下一个事件自己走出去（§5.2）。

### 5.2 上级侧：状态表 + 合并提醒

- 收到 `pg.attention` → 更新该子的活动状态表，**不注入**。
- 第一个未处理事件开窗（默认 300000 ms）。**`idle_owed` 不开窗**（见下）。
- 窗口到期：
  - 所有子的状态表都空了 → **静默取消**，不留痕迹。
  - 否则把一条汇总入队（`kind:'nudge'`），由投递窗口投出去。汇总本身不再看 `isBusy()`——投递是 steer。
    **可入汇总的状态不含 `idle_owed`**：否则全部子都只剩 `idle_owed` 时会投出一条只剩它的汇总，
    那正是本节要避免的那种注入。`blocked` 与 `silent_acking` **要进**——它们是父级能行动的那两条。
- 每行带着子成员上报的 last 块：最后一条助手正文与最后一个完成的工具调用（§8.5，概念稿）。
- **同一个状态的进入只提醒一次，没有超时重提。** 早先的规则是“同一状态持续超过 30 分钟再提醒一次”，
  它隐含一个假设：状态的“还在持续”能从子成员那里得到印证。子成员一死，这个假设就不成立了。
  父级要持续盯一个子，不应该靠重复推送——**它可以用 `pg_children()` 随时读这张表**，
  读完自己决定 `pg_inspect` / `pg_abort` / 自己干。推送只负责一件事：“这里发生了变化”。
- 同一个窗口里多个子的变化合并成一条；这是唯一的节流，理由是“醒一次就该看到全部”（同 §4.3）。
- **`idle_owed` 上报，但永不触发注入。** 债是会话级的，欠谁与父级无关：实测 64 条 `idle_owed`
  上报里共有 113 个 owed 引用、只涉及 15 个不同会话，其中 **101 个引用里父级不在那个会话里**（付不掉）。
  它留在表里供 `pg_children()` 查，但不该花掉一次全上下文请求去告诉父级一件它不能处理的事。
- `state:'gone'`（子被删）**立即**让窗到到期（不等 `remindWindowMs`），但**仍然只投一次**：
  同一刻多个子 gone 合并成一条汇总、一子一行。崩溃级联删除时这是关键——否则 15 个子就是 15 次全上下文请求。
  `gone` 报一次就从表里删掉，且它是终态：不发也不接受 `recovered`。
- `blocked` / `silent_acking` **走正常窗口合并**（最多晚一个 `remindWindowMs`），不走立即通道。
  理由：这两条信号前面已经过了多轮催办/确认，再晚一个窗口不损失行动时机；而 `gone` 要立即，
  因为父级可能正在等它的产物。
- **`blocked` 的“开口”与计数都按会话算**：`say(conv)` 只把 conv 从 `blocked` 集合里拿走、只清该会话的催办计数与
  blocked 去重标记；集合空才发 `recovered{of:'blocked'}`，否则重发一条带更小集合的 `blocked`。
  `pg_ack` **不**解除它——静默记账正是 `silent_acking` 要暴露的行为。
- **`silent_acking` 的四个维度**（不写清就无法实现）：作用域 = 会话；计数 = 该会话里**真正清掉 flag 的 ack**
  连续次数（no-op ack 不计，`pg_say` 一次就归零）；进入 = 计数到 3；离开 = 该会话里 `pg_say` 成功。

汇总的文本形态（**英文**；一个子一行，把自己所有活动状态列在这一行里；P7）：

```
2 children need attention:
- m_abc (reviewer) stalled 12m in bash: find ~/ -name '*.ts'
- m_def (coder) error: provider 429 x7, last at 14:03; blocked (2 convs: dm:m_a_m_d, dm:m_b_m_d)
```

### 5.3 工具

| 工具 | 谁用 | 行为 |
|---|---|---|
| `pg_members(query?)` | 成员 | 平台名册（`GET /v1/tree`）：id、名字、父、父名、关系、子数、`last_seen_at`；`total`/`matched` 让"查不到"和"打错名字"可区分。`last_seen_at` 是**最近一次鉴权**，不是存活 |
| `pg_children()` | 上级 | 返回遥测表快照（含每个下级的 last 块），不动模型上下文以外的任何东西 |
| `pg_inspect(member)` | 上级 | 发 `pg.inspect` 并等 `pg.inspect_result`，超时 10 秒；结果带 last 块 |
| `pg_abort(member?)` | 上级 | 对下级或自己发 `pg.abort`；切断后立刻关窗投递 |
| `pg_schedule(after_seconds, note)` | 成员 | 一次性唤醒：5 s–24 h，最多 8 条待触发，只在进程内；到点入投递队列，不绕过窗口 |
| `pg_say(to, text, mentions?)` | 成员 | 发消息，实现落在 `AdapterLoop.say()`（它顺手清掉义务）|
| `pg_ack(conv, seq?, all?)` | 成员 | 清掉一个会话的欠回复 flag，**不发消息**（§4.3）。与 `pg_say` 只共享一件事：都清 flag。它**不清**催办计数、**不清** blocked 上报的去重标记、**不结束**阻塞回合——“不开口”本身就是需要被看到的事，因此它另有自己的 `silent acking` 上报。`conv` 必填；清全部要显式 `all:true`（此时 `seq` 被忽略）；`seq` 不得超过本适配器为该会话点名过、投递过或 `pg_read` 读到过的最大序号 |
| `pg_read(conv, before?, limit?)` | 成员 | 读历史，用于 gap 回补或重读简报 |
| `pg_spawn(name?, brief, cwd?, args?)` | 成员 | `POST /members` + 发简报 DM + herdr 起 pane；pane 里的命令默认是本扩展的 `pi -e <自身绝对路径>`（§2.2），`PIGROUPS_SPAWN_CMD` 覆盖整条基础命令。`args` 是追加到基础命令后的原始 pi argv |
| `pg_terminate(member)` | 上级 | `DELETE /members/{id}`（级联）；剪掉级联返回的每个成员的私聊债；关掉本适配器记录过的、属于这些成员的 pane。返回 `{terminated, pane_close_failed, pane_close_forced}`——删除已经提交，关 pane 的失败只进第二个字段，强制切掉活 agent 的 pane 进第三个字段 |
| `pg_whoami()` | 成员 | 平台坐标 + 本适配器状态。返回 `{adapter_version, who, adapter}`：`adapter_version` 是本适配器版本（`src/version.ts`），`who.server.version` 是平台版本，两个都在答案里，人才知道这个成员跑的是哪一对 |


`pg_spawn` 的 `args` 是**原始 pi argv**：基础命令在前，`args` 的每一项按调用方给的顺序追加，一个元素一个 argv；`pane send-text` 兜底时再逐个 `shellQuote`。适配器不解释、不校验、不消毒这些元素——调用方可以传 `-p`、`--` 或任何改变子进程启动方式的旗标，那是调用方的选择（§2.2）。没有按参数名翻译成 pi 旗标的映射表：旗标以 `pi --help` 为准，模型不知道就自己去读。

`pg_abort` / `pg.steer` **只接受来自直接父或人的指令**；同群兄弟发来的记一条日志后忽略。这不是权限系统，是"适配器只响应自己的上级"。工具面上没有 `pg_steer`：改方向用 `pg_say`，`pg_steer` 只是线协议兼容。

**pane 的死亡路径有三条**，因为"谁删的"不一定是本进程：

1. 自己 `pg_terminate`：`spawn()` 按成员 id 记下 pane，`DELETE` 提交后关掉 `terminated` 里每个成员的 pane。
2. 祖先直接删本适配器的直接子成员：那是一次合法的 `DELETE`，但**不会**调用本进程的 `terminate()`。所以 `pollOnce()` 和 settle 都会拿 `GET /v1/members/{id}`（不是 30 秒的树快照）复核映射里的每个成员，**只关 `status:"gone"` 的**；每个成员最多每 30 秒查一次。读失败、404 都不关：错关会杀掉活成员的 shell，晚关什么也不丢。
3. pane 已经不在：`herdr pane close` 报 `pane_not_found` 是**成功**（shell 已经退出，或人手动关了）。其他 herdr 失败（daemon 挂了、超时）保留映射，报 `pane_close_failed` 等下一次重试——删除已提交，这个失败不能把 `pg_terminate` 变成工具错误。关掉了，但到点时 agent 还在运行的，报 `pane_close_forced`，不能伪装成干净关闭。

关之前先有界等待子 pi 收尾：`close()` 每 200 ms 读 `herdr pane list`，直到 pane 消失、或条目没有 `agent` / `agent_status=unknown`，最多 `PANE_AGENT_EXIT_TIMEOUT_MS = 5000`。`herdr` 没有“等 agent 自己退出”的命令，所以只能轮询；硬等一个卡住的 agent 会把工具拖到命令超时。**5 s 到点仍会关掉一个活着的 agent**——真机上 `bash sleep 40` 曾出现：`pane close` 时 `pane list` 仍报 `agent=pi working`，pi 在 close 之后才消失。`close()` 现在对这种情况返回 `forced: true`：`pg_terminate` 把它列进 `pane_close_forced`，祖先删除路径（settle/poll 复核）打一条 warn。`pane list` 读失败时不等待，也没有观察到活 agent，因此按 `forced: false` 处理。

**已知的两个缺口**（不是这段能修的）：映射只在内存里，适配器重启后丢失；子适配器自己拉起的孙子 pane，本进程从来没有映射。

## 6. `pg.*` 命令 schema

平台不认识这些，两端靠本文对齐。`v` 用于将来兼容；收到更高版本按未知处理（原样注入）。

```jsonc
// 子 → 父，控制通道
pg.attention   { v:1, child:"m_x", name:"…",
                 state:"stalled"|"slow_turn"|"error"|"idle_owed"
                      |"blocked"|"silent_acking"|"gone"
                      |"recovered",
                 since:1730000000000,
                 of?:"stalled"|"slow_turn"|"error"|"idle_owed"|"blocked"|"silent_acking",  // recovered 时必填；`gone` 是终态，不在此列
                 tool?:{name:"bash", elapsed_ms:720000, preview:"find ~/ …"},
                 owed?:["g:m_a"], note?:"no output after 3 nudges (dm:m_a_m_b)",
                 last?:{ text?:"最后一条助手正文（≤500 字）",
                         tool?:{ name:"edit", preview:"src/loop.ts", ok:true } } }

// 父 → 子，控制通道；子必须回 pg.inspect_result
pg.inspect     { v:1, request:"r-8f3a" }
pg.inspect_result { v:1, request:"r-8f3a",
                 phase:"idle"|"thinking"|"output"|"tool_call",
                 busy_ms:0, owed:["g:m_a"], children:2,
                 tool?:{name, elapsed_ms, preview},
                 last?:{ text?:"…", tool?:{name, preview, ok} } }

// 父或人 → 子
pg.abort       { v:1, reason?:"stalled 12m" }
pg.steer       { v:1, text:"先跑测试再继续" }
```

`id` 由发送方生成（`crypto.randomUUID()`），重发必须复用同一个，平台按 `(from_id,id)` 幂等。

**`pg.report` 已经删了。** 早先它打算装“成员的结论”（`done`/`progress`/`blocked`），但从未有过对应的工具：
成员汇报一直走 `pg_say`。实际只有两个生产者，而且都是适配器**替**成员说话（催满 3 次的 `blocked`、
退出时的 `exiting`），两者都有“进入→离开”的生命周期，因此并进 `pg.attention`（§5.1）。
一条通道、一套去重、一套窗口；跨进程只还剩 `pg.attention` 一种“子→父”的通知。

## 7. 配置

| 变量 | 默认 | 含义 |
|---|---|---|
| `PIGROUPS_URL` | 无 | 平台基址，如 `http://127.0.0.1:7717` |
| `PIGROUPS_TOKEN` | 无 | 本成员 token。缺失（或没有 URL）时不是成员：只注册 `pg_org_start`，不轮询 |
| `PIGROUPS_ADAPTER_DIR` | `~/.pigroups-adapter` | journal、本地状态、`orgs/<key>/`（每个组织一份记录与平台数据） |
| `PIGROUPS_POLL_LIMIT` | 20 | `poll` 的 limit |
| `PIGROUPS_POLL_WAIT` | 25 | 秒 |
| `PIGROUPS_ATTENTION_TOOL_MS` | 300000 | 单次工具调用多久算 stalled |
| `PIGROUPS_REMIND_WINDOW_MS` | 300000 | 上级合并提醒的窗口 |
| `PIGROUPS_NUDGE_MAX` | 3 | 同一会话最多催几次 |
| `PIGROUPS_DELIVERY_WINDOW_MS` | 60000 | 翻滚投递窗口。至少覆盖两次 25 s 的 poll |
| `PIGROUPS_SPAWN_CMD` | `pi -e <本扩展绝对路径>` | 在 pane 里启动什么。默认在正常 pi 环境上加载本扩展；显式值完全覆盖整条基础命令，路径有空格时要加引号。`pg_spawn` 的 `args` 追加在这条命令之后（§2.2） |
| `PIGROUPS_PLATFORM_DIR` | `../PiGroups` | 平台代码在哪里。`pg_org_start` 用它；测试也从这里拉起平台 |

`PIGROUPS_URL` 或 `PIGROUPS_TOKEN` 缺一个，这个会话就**没有身份**：扩展只注册 `pg_org_start`，
不轮询、不联网、不注册别的工具。两者都有时是普通成员，注册十一个成员工具，**不注册**
`pg_org_start`——一个已经有身份的会话不该有能力再开一个平台。

`pg_org_start` 起平台时自己生成 `PIGROUPS_ADMIN_TOKEN`（记录在 `org.json`，重接时沿用）；
它只是平台“建人”用的环境变量，不是适配器的配置。

## 8. 启动与退出

### 8.1 两条启动路径

**A. 有身份**（`PIGROUPS_URL` + `PIGROUPS_TOKEN`）：`session_start` 走下面的成员序列。

1. 打一行启动日志 `[pigroups] adapter <version> starting against <url>`；版本号来自 `src/version.ts`。版本串可以带 build metadata（这一版是 `0.6.0+platform.0.2.0`），metadata 只记录测试过的平台，不参与任何判定。
2. `GET /v1/whoami` → id / name / parent_id / is_root / groups。
3. 平台答完后，比较 `who.server.version` 的 major.minor 与 `SUPPORTED_PLATFORM_MINORS`（当前 `['0.2']`）。不在列表里只打**一条** warning，同时写出平台版本和本适配器版本，然后继续启动；平台连不上属于不可达，由循环的退避/上报处理，这里不 warn。匹配时什么也不打。
4. 若有父：读 `dm:<me>_<parent>` 的最后一条作为任务简报，注入一次（`kind:'message'`）。**启动简报不等投递窗口**（概念稿 §8.4）；其余入站项都等。
5. 全量对账义务表（§4.2）。
6. 重放 journal 里未注入的批次。
7. 启动轮询与 5 s 定时器。`pg_schedule` 的预约只在内存里，重启即失。

**B. 没有身份**：只注册 `pg_org_start`，`session_start` 什么也不做。工具成功之后构造与 A
相同的 `PiSurface` / `PgClient` / `Herdr` / `AdapterLoop`，注册其余十一个工具，并**当场**
启动循环（能调工具时 `session_start` 已经过去，不能再等一次事件）。同一会话再次调用
`pg_org_start` 直接回答"已属于 <url>"，不重建会话——重建会让两个循环用同一个 token 拉取。

### 8.2 `pg_org_start`：步骤与幂等

a. 读 `<adapterDir>/orgs/<key>/org.json`（key = 组织名；没给名字时用工作目录名，或复用唯一
   已存在的那个）。存在、`GET /v1/health` 答 `status:'ok'`、token 还能
   `GET /v1/whoami` → **重接**：返回 `reattached:true`，不启动任何进程。
b. 存在但平台不答 → 记录里的 pid 若还活着，先确认它确实是本平台（`/proc/<pid>/cmdline`
   或 `ps` 里含 `src/main.ts`）再 SIGTERM；确认不了就报错拒绝在同一个数据目录上起第二个。
   然后用原来的 data_dir/端口重启；token 仍有效就重接，否则尝试 bootstrap。
c. 没有记录（或需要新建）→ 找平台代码：`platform_dir` 参数 → `PIGROUPS_PLATFORM_DIR` →
   适配器仓库旁的 `../PiGroups` → `../../PiGroups`；判据只有一个：`src/main.ts` 存在。
   全都不存在 → 错误里列出**每一个**候选路径及来源。
d. 端口：参数优先；否则记录里的端口（若空闲）；否则系统分配。显式给的端口被占用就报错，
   不偷偷换一个。数据目录：`data_dir` 参数 → 记录里的 → `<adapterDir>/platform-data`。
e. `node <platform>/src/main.ts`，`detached:true` + `unref()`，stdout/stderr 追加到
   `<data_dir>/platform.log`；env 带 `PORT`、`PIGROUPS_DATA`、`PIGROUPS_ADMIN_TOKEN`
   （记录里有就沿用，否则随机生成）。
f. 轮询 `/v1/health`（默认 6 s）。**必须确认回答来自刚起的子进程**：若子进程已经退出而
   URL 仍有别的服务在答，算失败；否则会把一个死 pid 写进 `org.json`。
g. `POST /v1/bootstrap {name?}`（把 admin token 作为 Bearer 发出去；平台现在不校验它，
   以后校验也不用改适配器）。成功后把 `{url, token, admin_token, pid, data_dir}` 原子写入
   `org.json`（0600）。
h. 失败时停掉刚起的平台（SIGTERM，等 2 s，必要时 SIGKILL），不写 `org.json`，错误里带
   pid 和日志路径。

### 8.3 `org.json`

| 字段 | 含义 |
|---|---|
| `url` | 平台基址 |
| `token` | 根成员 token |
| `admin_token` | 起平台时用的管理员 token（平台建人用） |
| `pid` | 起平台时的进程号。**不是"它还活着"的证明**，只是重启/清理的线索 |
| `data_dir` | 平台的数据库与日志目录 |

目录 0700，文件 0600；先写临时文件再 `rename`，避免崩溃留下半份记录被下一次启动当真。

### 8.4 生命周期

- 平台**比根 session 活得久**：detached + unref + 日志落盘。`session_shutdown` 只停循环，
  不碰平台进程。
- 下一次会话用同一个 `PIGROUPS_ADAPTER_DIR` 调 `pg_org_start` 会重接；不会起第二个平台。
- `org.json` 是唯一的持久记录。删掉它等于"下一次开一个新组织"：适配器失去旧平台的 pid
  与端口，**不会**去杀它。数据目录默认仍是同一个 `<adapterDir>/platform-data`，所以旧平台
  还活着时，新启动会挑一个空闲端口，却和它写同一个 SQLite 库——两个进程、两个 URL、一份
  数据。要换新组织，先停掉旧 pid（或先调一次 `pg_org_start` 拿回记录再停），或者显式给一个
  新的 `data_dir`；只删 `org.json` 不够。
- 并发调用用 `<adapterDir>/org.lock` 串行化（内容为 pid + 时间；持有者进程已死或锁超过
  120 s 视为陈旧）。等待上限 15 s，超时报告而不是起第二个。

### 8.5 失败模式

| 情况 | 行为 |
|---|---|
| 找不到平台代码 | 列出全部候选路径与来源；不写任何文件 |
| 平台进程起不来 / 显式端口被占 | 报错；显式端口不自动换 |
| health 超时或子进程提前退出 | 停掉刚起的进程，错误里带 pid 与日志路径 |
| bootstrap 失败（409 `already_bootstrapped` 等） | 停掉刚起的进程，附平台错误码；不写 `org.json` |
| `org.json` 指向的平台健康但 token 被拒 | 报错并说明"停掉 pid、删 `org.json` 才能开新组织"；不叠第二个平台 |
| `org.json` 损坏 | 报错，需要人修或删 |

### 8.6 退出

**退出**（`session_shutdown` 或收到 `sys.terminated`）：
1. 尽力发一条 `pg.attention{state:'gone', note:'exiting'}` 给父，超时 2 秒即放弃。
   （退出路径不走循环，所以这一条直接由 `PgClient` 发；它不依赖遥测表、也不等窗口。）
2. 停循环。
3. `PgClient` 无连接可关；journal 已提交。
4. **不停止平台。** 组织不是这个 session 的附属物。

## 9. 错误与上限

| 情况 | 处置 |
|---|---|
| `poll` 409 `poll_in_progress` | 另一个本进程实例在拉；等 `Retry-After` 秒重试，连续 5 次后停 30 秒 |
| `poll` 410 `member_gone` | 停止一切，`shutdown()` |
| `poll` 401 | 停循环，等人工换 token。那条“token 失效”提示必须**先**投出去、再 `stop()`：停下来的循环一律拒投（`deliverPending` 直接答 `stopped`），顺序反了就烂在队列里。所以它按 `windowless` 项入队——和启动简报同一个例外：窗口是为了不打断工作，而这时已经没有工作可保护（发版前发现旧写法把它排到 `stop()` 之后，结果永远发不出去、而且没有日志；现在反过来，`test/control.test.ts` 有一条守着） |
| 平台连接失败 | 指数退避，上限 30 秒；连续 20 次后上报父 `blocked` 并停 |
| 单次 `deliver` 失败 | 保留 journal 与队列，等下一次窗口重试 |
| `pg.inspect` 超时 | 回一张 `phase:'unknown'` 的结果给自己，不编造 |
| `pg_org_start` 找不到平台代码 | 错误列出全部候选路径与来源，不写 `org.json` |
| `pg_org_start` bootstrap 失败 | 停掉刚起的平台，不写 `org.json`，错误带 pid 与日志路径 |

**不做的重试**：429。Pi 自己会重试，适配器只在"重试用尽且没有产出"时按 §4.3 报 `blocked`。

## 10. 测试策略

三条腿，都在 `npm test` 里：

1. **循环对假 PiSurface + 真平台**。测试起来一个真平台进程（`PIGROUPS_PLATFORM_DIR/src/main.ts`，`PORT` 与 `PIGROUPS_DATA` 用临时目录），假 surface 记录每一次 `deliver`/`abort`。断言的是**注入文本与顺序**，不是内部状态。
2. **命令 schema 双向**。发 `pg.inspect` → 断言对端收到 `pg.inspect_result` 且 `request` 对得上、带 last 块；`pg.attention` 六个状态各一条（其中带集合的三个再各测一次“集合变化重发”与“集合变空发 recovered”），带 last 块。
3. **假 Herdr**。`spawn` 断言发出的 herdr 参数、env、cwd；`waitReady` 超时路径。
4. **开组织端到端**（`test/orgstart.test.ts`）。调真工具：断言 `/v1/health` 与根身份、其余工具
   出现、第二个会话重接同一个平台、失败的 bootstrap 会杀掉自己刚起的平台、找不到平台时
   错误里列全候选路径、记录里的 pid 不是本平台时拒绝发信号。

**不测**：真实 `pi.sendMessage` 是否真能起一轮，真实 herdr 是否真能起 pane。这两件事只能在实机上验（§2.1 的三条）。测试替代品是接口，不是行为——这一点在 §2.1 写明了。

## 11. 非目标

- 命令拦截、白名单（不属于本插件）
- 相关性分类器（门控已取消，见概念稿 §7）
- 跨层遥测汇聚（一级，见概念稿 §6）
- 界面
- 平台侧任何改动

**`pg_children` 的列表来自平台，状态来自遥测。** 遥测只报异常（`stalled`/`slow_turn`/`error`/`idle_owed`/`blocked`/`silent_acking`），
所以一个刚派生、正在安静干活的下级**没有遥测条目**。工具若只列遥测表，父会在"刚派完活"这个最想
查看的时刻看到 `[]`。现在：`GET /v1/tree` 里 `parent_id` 是我的那些就是我的下级，逐行合并遥测；
没报过异常的行 `state` 是 `ok`。

**`agent start` 失败就是失败，不往 pane 里打字。** 旧的 `spawn` 在启动失败时把整条命令行
（含 `PIGROUPS_TOKEN=…`）`send-text` 进去；如果那个 pane 里已经有 pi 在跑，这行字会落进它的
输入框——人看到的是"无关文本出现在会话里"。只有 `PIGROUPS_SPAWN_CMD` 指向**非 pi 的包装命令**
时才走打字这条路，而且先确认 pane 里没有 agent。

### 派生的语义：交出去，不等就绪

`pg_spawn` 在子成员**启动**之后立刻返回 `{id, name}`。它不等子成员连上平台，也不等它跑完第一轮。

理由：派生是"把事交出去"。同步等待会让父在一个它并不需要此刻知道的事实上空转——实测中父
会为一次正常的派生阻塞十几秒甚至更久，而子成员早就在干活了。

就绪（D1：平台的 `last_seen_at` 非空）改由**后台**盯：`watchSpawnedMember` 在 `spawnReadyMs`
（默认 120 秒）内轮询，成功则静默；失败则往父自己的上下文里放一行 `[spawn] <名字> … never
connected` —— 子成员一直没连上，是父不该靠"注意不到它说话"才发现的事。

`agent start` 还有一个竞态：新建的 tab 里 shell 还没打印出提示符时，`agent start` 会失败。
所以那一步在 `AGENT_START_TIMEOUT_MS` 内**每 250 ms 重试**；仍然失败就是失败，**绝不**退化成
把命令行打字进 pane（那会把 `PIGROUPS_TOKEN=…` 送进别人的输入框）。
